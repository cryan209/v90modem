# CLAUDE.md

Gotchas and repo-specific knowledge for this project. Kept in sync with `AGENTS.md`; identical apart from this header.

## What this is

A SIP-based V.90/V.92 **digital-side** modem server. An analog client modem dials in over SIP; this software answers, runs the V.90 handshake over G.711 RTP, and bridges the data connection to a PTY.

The RTP payload **is** the DS0 PCM stream the far-end D/A converter sees. Most of the constraints below follow from that one fact.

## Constraints that silently break the modem

1. **Never transcode G.711.** No resampling, VAD/CNG, comfort noise, echo cancellation, or gain/AGC anywhere in the audio path. PCMU/PCMA codewords pass through byte-exact, for V.90, V.91 and V.92 alike. Passthrough is enabled via `PJMEDIA_HAS_PASSTHROUGH_CODECS` in `pj_config_site.h`.
2. **Never "clean up" DSP constants.** Scrambler taps, RRC coefficients, Ucode/µ-law tables and timing thresholds are ITU-spec values. Two scramblers coexist deliberately: downstream uses V.34 GPC (`1 + x^-18 + x^-23`), *not* the answer-modem GPA (`x^-5` tap). Conflating them is the classic silent breakage here — `v90.c:439`.
3. **Sample-rate error is fatal.** `clock_recovery.c` exists because a few ppm of drift destroys the constellation. Don't add buffering that changes sample accounting.
4. **Cite the spec when changing protocol logic.** ITU-T PDFs are in `ITU Docs/`. Reference section numbers in comments and commit messages, as the existing code does.

## Build and run

`make` builds `sip_v90_modem` and the test binaries. `make test` runs the suite (`data_stack_test`, `v42_link_test`, `v34_phase2_decode_test`, `v92_proc_eval_test`, `vpcm_loopback_test --all-tests`). Python harnesses are separate targets: `v32bis-ref-test`, `v32bis-datapump-test`, `v91-serial-pair-test`.

```bash
./sip_v90_modem --sip-server asterisk.net.cryan.nz --username 6001 --password 6001 --pty-link /tmp/v90modem
```

The PTY flag is `--pty-link`, not `--pty`; passing `--pty` is silently ignored and you get the default `/tmp/modem0`.

The automated tests only cover offline and loopback paths — passing them says nothing about hardware interop, which is verified manually against a real analog modem (`docs/v90_hardware_interop.md`).

Adding a source file means updating `SRCS` **and** the relevant `*_OBJS` lists in `makefile`; the test binaries link overlapping subsets, so a new dependency often needs adding in several places.

**The makefile has no header dependencies** (`%.o: %.c` at `makefile:243`, no `-MMD`). Editing a `.h` does not rebuild the `.c` files that include it, so a struct field added or reordered leaves stale objects linked against the old layout — the symptom is impossible values at runtime, not a link error. `rm` the affected `.o` files (or `make clean`) after touching any header.

**Commit straight to `main`.** This is a single-maintainer repo with a linear history; do not open a feature branch for a change unless asked. (Agent defaults often say to branch off the default branch — that default does not apply here.)

## Platform (macOS Apple Silicon)

- SpanDSP 3.0 builds from source in `spandsp-master/`. Do not substitute a system spandsp.
- `make` prefers the in-repo `pjproject/` tree when present, falling back to Homebrew.
- Both vendored trees are host-specific; `make` auto-`distclean`s and reconfigures when OS/arch changes.
- Override `ARCH_SUFFIX` only if linking a Homebrew pjproject with a different suffix: `ls "$(brew --prefix)/lib"/libpj-*.a | sed 's/.*libpj-//' | sed 's/\.a//'`

## Orientation

Layering that isn't obvious from filenames:

- `vpcm_*.c` is the shared V.PCM-family layer (CP helpers, G.711 stream, session and coupled-training plumbing) sitting under both the V.90 and V.92 paths. Protocol fixes usually belong here, not duplicated into `v90.c` and the `v92_*` modules.
- Not every decoder is live. `p3_demod.c` *is* — via `v90_cp_live.c` and `v92_p3_rx.c`. But `v34_phase2_decode.c`, `v34_info_decode.c`, `v8bis_decode.c`, `phase12_decode.c`, `v92_short_phase*_decode.c` and `v92_anspcm_decode.c` are absent from `SRCS` and reachable only from `vpcm_decode` and the test harnesses. Check `SRCS` in `makefile` before assuming a change affects real calls.
- `*_rrc.h`, `*_godard.h` and `v34_*_tables.h` are generated coefficient tables. Data, not hand-editable code.
- The Eicon Diva Server card work — the ADSP-2181 emulator, the MIPS firmware harness, the DIAL/INFO/V90D investigation tools and their 69-session analysis log — now lives in its own project, `../modem-dsp-emu`. It shares no code with this one: it runs the card's shipped firmware under emulation, rather than implementing the spec. `tools/cx_at.py` and `docs/courier_firmware_analysis.md` stayed here, and that project references them.
- `tools/` holds Python analysis and replay scripts; `captures/` and `artifacts/` hold recorded line audio and run outputs from hardware sessions.
- **`artifacts/` and `captures/` are gitignored, and only two directories are tracked.** A live run writes a new directory per call and the corpus reached 3.3 GB, so the history was rewritten to carry only what a build needs: `artifacts/eicon-digital-downstream/` and `artifacts/eicon-phase4-downstream/`, 648 KB, the fixtures `v90_analogue_rx_test` reads in `make test`. They are irreplaceable -- the only foreign downstream in the tree, the one receive test not fed by our own transmitter -- and the test does NOT skip without them: it reports a failure and exits 1. Everything else a working tree holds is local to the machine that recorded it. Two consequences. **The recordings the docs cite are evidence, not inputs a clone can obtain** -- `artifacts/reneg-eq/`, `reneg-ab-225015Z/`, `goal-matrix-115515Z/` and the rest are named all over `docs/` and in comments, and the offline reproductions built on them (`v90_engine_replay`, `v90_upstream_replay`) only run where the files are; a claim whose recording is gone cannot be re-checked, so re-derive rather than trusting it. And a tool that globs the corpus rather than naming a directory -- `tools/desplice_matrix.sh`, `tools/v90_upstream_bench.sh`, `tools/ja_concede_cost.py` and its 1345-call scan -- sees whatever is on the local disk and nothing on a clone, so check what is actually there before quoting an n. A new capture that a test depends on has to be `git add -f`'d.

Each module's header comment states its role and the spec sections it implements — read that before the `.c`.

- **The V.34 symbol-rate matrix was never run, and four defects were hiding behind 2400 baud (2026-08-21).** `v34_duplex_test` has always taken `<baud> <bps> <ulaw|alaw>`, but only 2400 was ever exercised; run across all six V.34 rates, every other rate timed out at 60 s with nothing trained. At 9600 bit/s it now trains **11 of the 12 rows and recovers payload without error on 10**, and `make test` asserts those ten (`make v34-matrix-test` runs all twelve without stopping at the first failure). Four defects, each hiding the next. (a) **The answerer's §11.3.1.2.6 J-wait bound was a flat 1000 ms**, which no conformant call modem can finish Phase 3 inside — S, S-bar, PP, 2048T of TRN and J exceed it at every symbol rate — so the interop escape fired on the *normal* path: the answerer abandoned J while the caller was still in TRN and ran ahead into Phase 4, leaving the caller waiting in J for an S that had already gone by. Now 4000 ms (`V34_J_WAIT_MAX_MS`). (b) **The receiver ran 2800 baud 1.56% off the symbol rate.** The T/2 accumulator advance is samples-per-symbol in units of 1/192 of a sample, and 2800 is the one rate whose value (192*20/7 = 548.57) is not a whole number of coefficient sets; the table wrote **189** in place of 192 for that row *alone* to force an integer. The remainder is now carried; the five exact rates are bit-identical. (c) **Phase 4 CMA never stopped** — its 512T bound is keyed on `phase4_trn_after_j`, which only advances once J' has been seen. It now stands down once the level estimate settles. (d) **Nothing ever chose which of the two T/2 outputs per symbol was the eye centre.** The band-edge detector recovers the symbol *rate* and pulls the phase within a T/2 interval but cannot resolve that ambiguity; it was settled by how many T/2 intervals had been generated since the receiver started, and a single ±1 correction from the timing loop can insert or delete one and flip it for the whole call. Sweeping a deliberate offset across a whole symbol on a bit-exact linear bearer, normalised distance to the nearest 4-point symbol through Phase 4: **2400 — offset 0: 0.384, one T/2 away: 0.590; 3200 — offset 0: 0.595 (the worst point of the entire sweep), one T/2 away: 0.293.** The receiver had been sampling 3200-baud Phase 4 *at the eye crossing*, and which way a call landed was a coin flip on sample counts — which is why the failures looked like thin margin and why every earlier change reshuffled which rows passed rather than growing the set. S, S-bar, PP, TRN and MP are all constant modulus, so the eye centre is where the equalized output is largest: both phases are now evaluated over 256 symbols during primary training and the larger taken, with a 1.05 margin, a minimum magnitude so the decision is never taken on §11.3.1.2.4's silence, and a flip cap. Parameters were chosen over 24 rows (both laws at 4800 *and* 9600) so as not to fit the twelve `make test` asserts. Open: 3429 u-law does not train; 3000 u-law trains with 136 payload errors. **Two metrics here are traps and both were believed for a while: 4th-power coherence over the Phase 4 TRN dump reads 0.39–0.47 whether the call completes with zero errors or never trains, and the MP-stage `[EQ]` decision error has its target angle integrated from the *received* dibit, so it measures constellation tightness rather than decode correctness (3429 reads 0.048 and 2800 0.042 while neither trains). What is trustworthy: ground truth against the transmitter's own symbols (`V34_P4TRN_TX_DUMP`/`V34_P4TRN_RX_DUMP` + `tools/v34_trn_ground_truth.py`), and sweeping the sampling instant for the minimum — which is what found (d).** Diagnostics, all opt-in and all caching their getenv: `V34_P3TRN_SYM_DUMP`/`V34_P4TRN_SYM_DUMP` (symbol, line power, tap energy, main tap, sampling phase), `V34_MP_TX_BITS`, `V34_TRACE`, `V34_DUPLEX_LOG`, `V34_DUPLEX_TXRMS`, and `V34_DUPLEX_LINEAR` to bypass G.711 and so attribute a defect to the bearer or exonerate it. — `docs/v34_spec_gap.md` item 5.

- **Upstream payload now arrives (2026-08-20).** The lottery was a *two-dimensional* frame-phase ambiguity, not one: B1 does not tell us the peer's superframe counter, and its end pins the position *within* the data frame only if B1 ends exactly where we think. Sweeping the seven superframe phases alone enumerated cleanly on a live call and found nothing; sweeping the **(superframe, data-frame) pair** — p×j = 112 candidates at a 0.4 s window, under a minute — locks, applied by the decoder at its own frame boundary so a step never disturbs alignment. Live at 9600 upstream with the peer trickling 200 B/s: **downstream 38830/39025 lines 99.5% clean, upstream 1329 pattern lines in sequence with one missing** — the peer's actual data (`U0000500`, `U0000501`, … unbroken) on our PTY for the first time. Across five consecutive calls the sweep locked six times (0, 1, 2, 35, 102, 128 steps; 78–100% ones) and three delivered payload. A lock is released and re-swept when the ones-fraction falls back. **Open:** a lock holds ~27 s and then decays as the Gardner slip count jumps (7→12 in a few seconds), so holding a lock — not finding one — is now the problem. Note the byte-level "% clean" figures understate results badly; they count the garbage emitted while unlocked, so the *line* counts are the honest measure. Timing recovery itself is `v34_gardner.h` + `v34_gardner_test` (S-curve, acquisition, 50 ppm tracking, quiescence) — and in this receiver the matched filter is the adaptive FSE, so the detector reads the equalizer output, not the fixed RRC. — `docs/v90_upstream_data_path.md`.
- **The upstream slip carries a carrier step (2026-08-21).** The peer's slips are now *measured* rather than inferred: `tools/measure_timing_slips.py` reads the transmitter's symbol epoch off a recorded tap, out of the phase of the symbol-rate line in the squared analytic envelope, and one 8 kHz sample moves it by exactly 360 x baud/8000 degrees. On `artifacts/dmodem-soak-0821-rounds/round1` the peer steps by one sample **28 times in 290 s**, net +7.2 ppm, in bursts of three a second apart -- while the RTP is unbroken across every one (21365 packets, no loss, no timestamp jump, media clock within 4 ppm), so the slips are in the peer's audio generation, not the transport. The receiver had been reporting **81** corrections against those 28 events. Four defects, each hiding the next. (a) **The slip search span was wider than the thing it searched.** The lattice score is periodic in one symbol -- three samples at T/3 -- so +/-3 samples offered every minimum twice, once a whole symbol away, and the argmin chose on noise: 46 of 81 corrections were the far copy (36 of them "+2.67" = -0.33 plus a symbol), each moving the shell decoder within the data frame, which the frame-phase sweep cannot undo because it searches frame labels rather than single symbols. Now the half symbol either side, in sixths -- a slip is 1.2 T/3 samples at 3200 baud and a thirds grid has no point within 0.13 of it. (b) **A slip is a passband delay, so it comes with a rotation.** The T/3 ring holds baseband mixed on the absolute sample count, so reading D samples on recovers the right sample *rotated by -wD* -- 82 degrees per sample at 3200 baud low carrier. The search corrected the delay and left the rotation, which is exactly why it kept reporting a flat profile at 0.65 with nothing to choose between candidates: the right instant was in the list and still did not fit the lattice. It also explains the "lottery" -- 82 degrees is near enough to 90, which V.34's differential mapping makes harmless, that the fourth-power estimator sometimes recovered a call unaided. The scorer now derotates by the carrier loop's standing phase (which it never did, so it had been scoring a signal the slicer does not see) and by the offset's implied phase, and an adopted offset carries its rotation into the loop. (c) **Everything adaptive gated on a 256-symbol average**, so the DD-LMS adapted hard onto wrong decisions for ~100 symbols after each slip and walked off the very filter the search needs; a 1/16 estimate now gates the LMS, timing and carrier loops, and the search runs after 48 symbols off the constellation rather than 240. (d) **The frame-phase sweep could not return to its own best candidate** -- it recorded absolute (super_frame, data_frame) pairs, which are free-running counters, so writing one back at a later boundary lands elsewhere; the phase is now a relative shift with an accumulated position that names the candidate. An equalizer restore also reset the sweep counter, and restores fire every 375 ms, so on round1 the sweep never passed step 1 of 112 in five minutes. **Worth:** symbols on the lattice **35.8% -> 60.1%** of the call and the permanent collapse is gone (68 s clean, then white for 145 s with the wire provably quiet; now recovers in 20 s and runs 73 s clean), with real pattern lines reaching the PTY in bursts. **Open:** frame-phase lock still does not hold -- 60% of the call has an open eye and only a few percent is framed right. The release rule cannot be right on a line carrying data: the soak pattern is mostly digits, which through V.14 read 30-40% ones, so a correct decode looks like noise to a rule that releases below 70%. Measured on the one stretch that provably carries payload, the V.14 metric reads 32% at 1.4x -- honest, and about a sixth of the lines. `v90_upstream_replay` reproduces all of it in 75 s. -- `docs/v90_upstream_data_path.md`
- **The upstream lock metric could not see a correct decode of real data (2026-08-21).** **5217 pattern lines off the peer where the same recording gave 14**, 5129 of the gaps between them exact multiples of the 90-bit line -- runs of its actual traffic. The frame-phase lock was released whenever the descrambled stream read under 70% ones, which is right for an idle DTE and exactly wrong for one that is sending: the soak pattern is mostly digits, `'0'` is 0x30, and LSB-first between a zero start bit and a one stop bit that is three ones in ten, so a *perfect* decode reads 30-40% ones. The receiver was finding the phase, decoding correctly, and discarding the lock the moment the peer said anything -- which is what "a lock holds about half a second" had always been. The evidence needed was already computed and discarded: §9.6.3.3 builds the shell index r0 from the ring indices of a mapping frame's eight 2D symbols and the transmitter's construction bounds it to k bits, so an r0 that does not fit cannot have come from a correctly grouped frame -- a frame-phase check that owes nothing to the content. `bitstream_put()` truncates silently, so nothing had looked. Measured over round1: correct-phase windows read 0% in 194 of 202 and never above 3%, wrong-phase windows 3% or more in 92 of every 100. A standing lock is now judged on that (falling back on the marks only where k is zero), and the sweep ranks candidates by it first. **Read line counts, not the ones fraction, from here on** -- it was the right instrument only while the peer was idle. -- `docs/v90_upstream_data_path.md`

Phase 4 (§9.4) does not exist: the engine logs the DIL measurement and the constellation it implies, then hangs up (`ME_V90_ANALOGUE_HOLD=1` keeps the call up for capture). `v90_analogue_rx_test` in `make test` runs the receive path against `artifacts/eicon-digital-downstream/` — the only downstream here we did not generate — reading Sd 64 reps, S̄d 8, TRN1d 30000T and 13–14 CRC-valid Jd frames, then driving the transmitter to Phase 4 off that real signal. **Two conventions the fixture caught, both invisible to loopback: Sd's zero slots must match on level, not codeword** (a working modem sends +0 in every zero slot, and since those slots match Sd and S̄d equally, counting them hides the §9.3.2.4 transition entirely), **and TRN1d is not differentially encoded** — §8.4.5 puts the scrambler output straight on the sign, and only Jd adds §8.4.2's differential encoder; decoding TRN1d differentially yields a clean stream of zeros and truncates it. **Live against the Eicon card under emulation (2026-08-10) the analogue side now completes Phase 2 and drives the card onto its V.90 page** (`INFO_RX complete=1`, `bootpage 7 -> 14 V.90 DPCM`). Three fixes got there, each found by a call: §9.2.2.1.8 — the analogue modem transmits **Tone A** after L1/L2 and answers with INFO1a only after INFO1d (SpanDSP took the V.34 call-modem branch and sent INFO1a immediately, which deadlocks, because §9.2.1.1.7 has the digital modem waiting to detect Tone A before it sends INFO1d); this card **never sends INFO1d at all** and waits for INFO1a, whose bits 37:39 pick its V.90 page, so `ME_V90_ANALOGUE_INFO1D_TIMEOUT=info1a` sends it anyway (opt-in — it is not one of §9.2.2.2.4's two responses, and the conformant INFOMARKSa *replaces* the Tone A the peer wants); and INFO1a is now repeated as a §8.2.3.1 group (4 by default, `ME_V90_ANALOGUE_INFO1A_REPEATS`) exactly as the digital side already repeats INFO1d. It then stops: the card enters page 14 and transmits no Sd. **That is most likely still ours** — the same card under the same emulation has reached V.90 data mode against two real analogue modems, needing neither workaround, and §9.3.1.1-9.3.1.3 make Sd conditional on the digital modem *detecting Ja*, which our transmitter has no foreign grader for. **The §9.2.2.1.3-9.2.2.1.6 tone choreography is now fixed** (2026-08-10): the analogue role was running SpanDSP's V.34 *call modem* tone stages, because `initial_ab_not_ab_baud_init()` picked the stage family off `calling_party` alone. The frequency was right by accident (the analogue modem already gets the 2400 Hz CC carrier, which is Tone A); the *timetable* was not. **Which tone a modem transmits follows its role, not the call direction** — V.34 gives Tone A to the answer modem (§11.2.1.2) and Tone B to the call modem (§11.2.1.1), and V.90 keeps both timetables but hands them to the other end of the call, so §9.2.2.1 is §11.2.1.2 word for word with INFO0d/INFO1d for INFO0c/INFO1c and the Tone A transmitter is the side where `calling_party` and `v90_mode` agree (the same predicate `v34rx.c` already used to pick the receive carrier). The correct choreography was therefore already in the tree as the V.34 answer-modem A family, just unreachable. Three fixes in `v34tx.c`: the stage family now routes on the role; the end of the analogue's own L1/L2 goes to `second_a_baud_init()` rather than `pre_info1_a_init()`, because §9.2.2.1.5's probe is only the first of two rounds and jumping to Tone A skipped the §9.2.2.1.6 Tone A/reversal/silence that §9.2.1.1.6 times its Tone B reversal against (the digital modem sat in `SECOND_B` and never sent INFO1d); and `FIRST_A` now waits for the peer's tone to be *detected* as well as its INFO0 received, which is what §9.2.2.1.3 literally says — reversing on `INFO0_OK` alone is only equivalent when the peer's tone is already up, and in V.90 it never is, because §9.2.1.1.1-9.2.1.1.2 have the digital modem start Tone B *after* it receives INFO0a (that third one is gated to V.90: §11.2.1.2.3 says the same, but the V.34 answer modem's receiver sits in `V34_RX_STAGE_TONE_B`, whose detector never publishes `TONE_SEEN`, so requiring it there would deadlock plain V.34). ## Fax service class (T.31 class 1, T.32 class 2.0)

`AT+FCLASS=?` reports `0,1,1.0,2.0`. `0` is the data modem and is unchanged.

`1`/`1.0` is T.31 class 1: T.30 stays in the DTE, the class 1 action commands
(`+FTS`, `+FRS`, `+FTM`, `+FRM`, `+FTH`, `+FRH`) work, and the call's audio
goes to SpanDSP's T.31 fax datapumps rather than through V.8 and the V.90/V.34
startup. The AT interpreter is a `t31_state_t`, not a bare `at_init()` — that
is what supplies the class 1 handler. Without one the `+F` commands parse and
then answer `ERROR`, which reads as a working interface and is not.

`2.0` is T.32 class 2.0, where **the DCE runs T.30**: `fax_class2.c` is a T.32
command layer over SpanDSP's `fax_state_t`, with `t4_rx`/`t4_tx` bridging the
DTE's compressed image data to the TIFF files T.30 transfers. SpanDSP's own
class 2 command handlers are `TODO` stubs and are not used. One deviation is
deliberate and documented: `+FDT` takes the page before it reports `+FCS`,
because SpanDSP's T.30 needs the document to exist by the DIS it receives.
`+FBO`'s phase C bit order is applied — the default order is LSB first, the
same one T.31's class 1 path uses with no reversal. `+FNR` negotiation
reporting is implemented off SpanDSP's real-time frame handler, and so are
`+FBU`'s `+FHT:`/`+FHR:` frame reports, `+FNS` non-standard frames and polling
(`+FLP`, `+FSP`, `+FPO`) and procedure interrupts (`+FIE`, `+FVO`, `<DLE><pri>`
— which needed a small addition to SpanDSP's receiver, where answering PIP/PIN
was an empty TODO). The post page response is **held** for the DTE per 8.3.4.3,
so a receiving session needs one more `+FDR` than it has pages; that needed a
second SpanDSP addition (`t30_set_post_page_response_hold()`). **Watch the FCF
low bit**: in DIS/DTC, CSI/CIG and
NSF/NSC it is a real distinction, but in DCS, TSI and NSS it is a don't-care
set from whether a DIS was received, so those must be matched with `& 0xFE` —
matching TSI exactly reported every calling station's TSI as a CSI.

**The T-series specifications are in `ITU Docs/`** — T.31, T.32 (+ Amd 1),
T.30, T.4, T.6 — and reading T.32 against code that had been written from
SpanDSP's headers and internal evidence found four real defects (the `+FHS`
codes assigned across the wrong phases and directions, `+FCS:` not suppressed
by `+FNR`'s tpr, `+FPS:` missing its four line counts, `+FDT` not ending in
`ERROR` on a rejected page). Read the clause before extending this.

Neither class has hardware interop. See `docs/fax_class_at.md`.

`docs/` holds a design note or investigation write-up per phase. Read the relevant one before changing that phase.
