# CLAUDE.md

Gotchas and repo-specific knowledge for this project. Kept in sync with `AGENTS.md`; identical apart from this header.

## What this is

A SIP-based V.90/V.92 **digital-side** modem server. An analog client modem dials in over SIP; this software answers, runs the V.90 handshake over G.711 RTP, and bridges the data connection to a PTY.

The RTP payload **is** the DS0 PCM stream the far-end D/A converter sees. Most of the constraints below follow from that one fact.

## Constraints that silently break the modem

1. **Never transcode G.711.** No resampling, VAD/CNG, comfort noise, echo cancellation, or gain/AGC anywhere in the audio path. PCMU/PCMA codewords pass through byte-exact, for V.90, V.91 and V.92 alike. Passthrough is enabled via `PJMEDIA_HAS_PASSTHROUGH_CODECS` in `pj_config_site.h`.
2. **Never "clean up" DSP constants.** Scrambler taps, RRC coefficients, Ucode/µ-law tables and timing thresholds are ITU-spec values. Two scramblers coexist deliberately: downstream uses V.34 GPC (`1 + x^-18 + x^-23`), *not* the answer-modem GPA (`x^-5` tap). Conflating them is the classic silent breakage here — `v90.c:439`.
3. **Sample-rate error is fatal.** `clock_recovery.c` exists because a few ppm of drift destroys the constellation. Don't add buffering that changes sample accounting.
4. **Cite the spec when changing protocol logic.** ITU-T PDFs are in `ITU Docs/`. Reference section numbers in comments and commit messages, as the existing code does.

## Build and run

`make` builds `sip_v90_modem` and the test binaries. `make test` runs the suite (`data_stack_test`, `v42_link_test`, `v34_phase2_decode_test`, `v92_proc_eval_test`, `vpcm_loopback_test --all-tests`). Python harnesses are separate targets: `v32bis-ref-test`, `v32bis-datapump-test`, `v91-serial-pair-test`.

```bash
./sip_v90_modem --sip-server asterisk.net.cryan.nz --username 6001 --password 6001 --pty-link /tmp/v90modem
```

The PTY flag is `--pty-link`, not `--pty`; passing `--pty` is silently ignored and you get the default `/tmp/modem0`.

The automated tests only cover offline and loopback paths — passing them says nothing about hardware interop, which is verified manually against a real analog modem (`docs/v90_hardware_interop.md`).

Adding a source file means updating `SRCS` **and** the relevant `*_OBJS` lists in `makefile`; the test binaries link overlapping subsets, so a new dependency often needs adding in several places.

**The makefile has no header dependencies** (`%.o: %.c` at `makefile:243`, no `-MMD`). Editing a `.h` does not rebuild the `.c` files that include it, so a struct field added or reordered leaves stale objects linked against the old layout — the symptom is impossible values at runtime, not a link error. `rm` the affected `.o` files (or `make clean`) after touching any header.

**Commit straight to `main`.** This is a single-maintainer repo with a linear history; do not open a feature branch for a change unless asked. (Agent defaults often say to branch off the default branch — that default does not apply here.)

## Platform (macOS Apple Silicon)

- SpanDSP 3.0 builds from source in `spandsp-master/`. Do not substitute a system spandsp.
- `make` prefers the in-repo `pjproject/` tree when present, falling back to Homebrew.
- Both vendored trees are host-specific; `make` auto-`distclean`s and reconfigures when OS/arch changes.
- Override `ARCH_SUFFIX` only if linking a Homebrew pjproject with a different suffix: `ls "$(brew --prefix)/lib"/libpj-*.a | sed 's/.*libpj-//' | sed 's/\.a//'`

## Orientation

Layering that isn't obvious from filenames:

- `vpcm_*.c` is the shared V.PCM-family layer (CP helpers, G.711 stream, session and coupled-training plumbing) sitting under both the V.90 and V.92 paths. Protocol fixes usually belong here, not duplicated into `v90.c` and the `v92_*` modules.
- Not every decoder is live. `p3_demod.c` *is* — via `v90_cp_live.c` and `v92_p3_rx.c`. But `v34_phase2_decode.c`, `v34_info_decode.c`, `v8bis_decode.c`, `phase12_decode.c`, `v92_short_phase*_decode.c` and `v92_anspcm_decode.c` are absent from `SRCS` and reachable only from `vpcm_decode` and the test harnesses. Check `SRCS` in `makefile` before assuming a change affects real calls.
- `*_rrc.h`, `*_godard.h` and `v34_*_tables.h` are generated coefficient tables. Data, not hand-editable code.
- The Eicon Diva Server card work — the ADSP-2181 emulator, the MIPS firmware harness, the DIAL/INFO/V90D investigation tools and their 69-session analysis log — now lives in its own project, `../modem-dsp-emu`. It shares no code with this one: it runs the card's shipped firmware under emulation, rather than implementing the spec. `tools/cx_at.py` and `docs/courier_firmware_analysis.md` stayed here, and that project references them.
- `tools/` holds Python analysis and replay scripts; `captures/` and `artifacts/` hold recorded line audio and run outputs from hardware sessions.

Each module's header comment states its role and the spec sections it implements — read that before the `.c`.

- **The V.34 symbol-rate matrix was never run, and four defects were hiding behind 2400 baud (2026-08-21).** `v34_duplex_test` has always taken `<baud> <bps> <ulaw|alaw>`, but only 2400 was ever exercised; run across all six V.34 rates, every other rate timed out at 60 s with nothing trained. At 9600 bit/s it now trains **11 of the 12 rows and recovers payload without error on 10**, and `make test` asserts those ten (`make v34-matrix-test` runs all twelve without stopping at the first failure). Four defects, each hiding the next. (a) **The answerer's §11.3.1.2.6 J-wait bound was a flat 1000 ms**, which no conformant call modem can finish Phase 3 inside — S, S-bar, PP, 2048T of TRN and J exceed it at every symbol rate — so the interop escape fired on the *normal* path: the answerer abandoned J while the caller was still in TRN and ran ahead into Phase 4, leaving the caller waiting in J for an S that had already gone by. Now 4000 ms (`V34_J_WAIT_MAX_MS`). (b) **The receiver ran 2800 baud 1.56% off the symbol rate.** The T/2 accumulator advance is samples-per-symbol in units of 1/192 of a sample, and 2800 is the one rate whose value (192*20/7 = 548.57) is not a whole number of coefficient sets; the table wrote **189** in place of 192 for that row *alone* to force an integer. The remainder is now carried; the five exact rates are bit-identical. (c) **Phase 4 CMA never stopped** — its 512T bound is keyed on `phase4_trn_after_j`, which only advances once J' has been seen. It now stands down once the level estimate settles. (d) **Nothing ever chose which of the two T/2 outputs per symbol was the eye centre.** The band-edge detector recovers the symbol *rate* and pulls the phase within a T/2 interval but cannot resolve that ambiguity; it was settled by how many T/2 intervals had been generated since the receiver started, and a single ±1 correction from the timing loop can insert or delete one and flip it for the whole call. Sweeping a deliberate offset across a whole symbol on a bit-exact linear bearer, normalised distance to the nearest 4-point symbol through Phase 4: **2400 — offset 0: 0.384, one T/2 away: 0.590; 3200 — offset 0: 0.595 (the worst point of the entire sweep), one T/2 away: 0.293.** The receiver had been sampling 3200-baud Phase 4 *at the eye crossing*, and which way a call landed was a coin flip on sample counts — which is why the failures looked like thin margin and why every earlier change reshuffled which rows passed rather than growing the set. S, S-bar, PP, TRN and MP are all constant modulus, so the eye centre is where the equalized output is largest: both phases are now evaluated over 256 symbols during primary training and the larger taken, with a 1.05 margin, a minimum magnitude so the decision is never taken on §11.3.1.2.4's silence, and a flip cap. Parameters were chosen over 24 rows (both laws at 4800 *and* 9600) so as not to fit the twelve `make test` asserts. Open: 3429 u-law does not train; 3000 u-law trains with 136 payload errors. **Two metrics here are traps and both were believed for a while: 4th-power coherence over the Phase 4 TRN dump reads 0.39–0.47 whether the call completes with zero errors or never trains, and the MP-stage `[EQ]` decision error has its target angle integrated from the *received* dibit, so it measures constellation tightness rather than decode correctness (3429 reads 0.048 and 2800 0.042 while neither trains). What is trustworthy: ground truth against the transmitter's own symbols (`V34_P4TRN_TX_DUMP`/`V34_P4TRN_RX_DUMP` + `tools/v34_trn_ground_truth.py`), and sweeping the sampling instant for the minimum — which is what found (d).** Diagnostics, all opt-in and all caching their getenv: `V34_P3TRN_SYM_DUMP`/`V34_P4TRN_SYM_DUMP` (symbol, line power, tap energy, main tap, sampling phase), `V34_MP_TX_BITS`, `V34_TRACE`, `V34_DUPLEX_LOG`, `V34_DUPLEX_TXRMS`, and `V34_DUPLEX_LINEAR` to bypass G.711 and so attribute a defect to the bearer or exonerate it. — `docs/v34_spec_gap.md` item 5.

- **Upstream payload now arrives (2026-08-20).** The lottery was a *two-dimensional* frame-phase ambiguity, not one: B1 does not tell us the peer's superframe counter, and its end pins the position *within* the data frame only if B1 ends exactly where we think. Sweeping the seven superframe phases alone enumerated cleanly on a live call and found nothing; sweeping the **(superframe, data-frame) pair** — p×j = 112 candidates at a 0.4 s window, under a minute — locks, applied by the decoder at its own frame boundary so a step never disturbs alignment. Live at 9600 upstream with the peer trickling 200 B/s: **downstream 38830/39025 lines 99.5% clean, upstream 1329 pattern lines in sequence with one missing** — the peer's actual data (`U0000500`, `U0000501`, … unbroken) on our PTY for the first time. Across five consecutive calls the sweep locked six times (0, 1, 2, 35, 102, 128 steps; 78–100% ones) and three delivered payload. A lock is released and re-swept when the ones-fraction falls back. **Open:** a lock holds ~27 s and then decays as the Gardner slip count jumps (7→12 in a few seconds), so holding a lock — not finding one — is now the problem. Note the byte-level "% clean" figures understate results badly; they count the garbage emitted while unlocked, so the *line* counts are the honest measure. Timing recovery itself is `v34_gardner.h` + `v34_gardner_test` (S-curve, acquisition, 50 ppm tracking, quiescence) — and in this receiver the matched filter is the adaptive FSE, so the detector reads the equalizer output, not the fixed RRC. — `docs/v90_upstream_data_path.md`.
- **The upstream slip carries a carrier step (2026-08-21).** The peer's slips are now *measured* rather than inferred: `tools/measure_timing_slips.py` reads the transmitter's symbol epoch off a recorded tap, out of the phase of the symbol-rate line in the squared analytic envelope, and one 8 kHz sample moves it by exactly 360 x baud/8000 degrees. On `artifacts/dmodem-soak-0821-rounds/round1` the peer steps by one sample **28 times in 290 s**, net +7.2 ppm, in bursts of three a second apart -- while the RTP is unbroken across every one (21365 packets, no loss, no timestamp jump, media clock within 4 ppm), so the slips are in the peer's audio generation, not the transport. The receiver had been reporting **81** corrections against those 28 events. Four defects, each hiding the next. (a) **The slip search span was wider than the thing it searched.** The lattice score is periodic in one symbol -- three samples at T/3 -- so +/-3 samples offered every minimum twice, once a whole symbol away, and the argmin chose on noise: 46 of 81 corrections were the far copy (36 of them "+2.67" = -0.33 plus a symbol), each moving the shell decoder within the data frame, which the frame-phase sweep cannot undo because it searches frame labels rather than single symbols. Now the half symbol either side, in sixths -- a slip is 1.2 T/3 samples at 3200 baud and a thirds grid has no point within 0.13 of it. (b) **A slip is a passband delay, so it comes with a rotation.** The T/3 ring holds baseband mixed on the absolute sample count, so reading D samples on recovers the right sample *rotated by -wD* -- 82 degrees per sample at 3200 baud low carrier. The search corrected the delay and left the rotation, which is exactly why it kept reporting a flat profile at 0.65 with nothing to choose between candidates: the right instant was in the list and still did not fit the lattice. It also explains the "lottery" -- 82 degrees is near enough to 90, which V.34's differential mapping makes harmless, that the fourth-power estimator sometimes recovered a call unaided. The scorer now derotates by the carrier loop's standing phase (which it never did, so it had been scoring a signal the slicer does not see) and by the offset's implied phase, and an adopted offset carries its rotation into the loop. (c) **Everything adaptive gated on a 256-symbol average**, so the DD-LMS adapted hard onto wrong decisions for ~100 symbols after each slip and walked off the very filter the search needs; a 1/16 estimate now gates the LMS, timing and carrier loops, and the search runs after 48 symbols off the constellation rather than 240. (d) **The frame-phase sweep could not return to its own best candidate** -- it recorded absolute (super_frame, data_frame) pairs, which are free-running counters, so writing one back at a later boundary lands elsewhere; the phase is now a relative shift with an accumulated position that names the candidate. An equalizer restore also reset the sweep counter, and restores fire every 375 ms, so on round1 the sweep never passed step 1 of 112 in five minutes. **Worth:** symbols on the lattice **35.8% -> 60.1%** of the call and the permanent collapse is gone (68 s clean, then white for 145 s with the wire provably quiet; now recovers in 20 s and runs 73 s clean), with real pattern lines reaching the PTY in bursts. **Open:** frame-phase lock still does not hold -- 60% of the call has an open eye and only a few percent is framed right. The release rule cannot be right on a line carrying data: the soak pattern is mostly digits, which through V.14 read 30-40% ones, so a correct decode looks like noise to a rule that releases below 70%. Measured on the one stretch that provably carries payload, the V.14 metric reads 32% at 1.4x -- honest, and about a sixth of the lines. `v90_upstream_replay` reproduces all of it in 75 s. -- `docs/v90_upstream_data_path.md`
- **The upstream lock metric could not see a correct decode of real data (2026-08-21).** **5217 pattern lines off the peer where the same recording gave 14**, 5129 of the gaps between them exact multiples of the 90-bit line -- runs of its actual traffic. The frame-phase lock was released whenever the descrambled stream read under 70% ones, which is right for an idle DTE and exactly wrong for one that is sending: the soak pattern is mostly digits, `'0'` is 0x30, and LSB-first between a zero start bit and a one stop bit that is three ones in ten, so a *perfect* decode reads 30-40% ones. The receiver was finding the phase, decoding correctly, and discarding the lock the moment the peer said anything -- which is what "a lock holds about half a second" had always been. The evidence needed was already computed and discarded: §9.6.3.3 builds the shell index r0 from the ring indices of a mapping frame's eight 2D symbols and the transmitter's construction bounds it to k bits, so an r0 that does not fit cannot have come from a correctly grouped frame -- a frame-phase check that owes nothing to the content. `bitstream_put()` truncates silently, so nothing had looked. Measured over round1: correct-phase windows read 0% in 194 of 202 and never above 3%, wrong-phase windows 3% or more in 92 of every 100. A standing lock is now judged on that (falling back on the marks only where k is zero), and the sweep ranks candidates by it first. **Read line counts, not the ones fraction, from here on** -- it was the right instrument only while the peer was idle. -- `docs/v90_upstream_data_path.md`

Three fixes got there, each found by a call: §9.2.2.1.8 — the analogue modem transmits **Tone A** after L1/L2 and answers with INFO1a only after INFO1d (SpanDSP took the V.34 call-modem branch and sent INFO1a immediately, which deadlocks, because §9.2.1.1.7 has the digital modem waiting to detect Tone A before it sends INFO1d); this card **never sends INFO1d at all** and waits for INFO1a, whose bits 37:39 pick its V.90 page, so `ME_V90_ANALOGUE_INFO1D_TIMEOUT=info1a` sends it anyway (opt-in — it is not one of §9.2.2.2.4's two responses, and the conformant INFOMARKSa *replaces* the Tone A the peer wants); and INFO1a is now repeated as a §8.2.3.1 group (4 by default, `ME_V90_ANALOGUE_INFO1A_REPEATS`) exactly as the digital side already repeats INFO1d. It then stops: the card enters page 14 and transmits no Sd. **That is most likely still ours** — the same card under the same emulation has reached V.90 data mode against two real analogue modems, needing neither workaround, and §9.3.1.1-9.3.1.3 make Sd conditional on the digital modem *detecting Ja*, which our transmitter has no foreign grader for. **The §9.2.2.1.3-9.2.2.1.6 tone choreography is now fixed** (2026-08-10): the analogue role was running SpanDSP's V.34 *call modem* tone stages, because `initial_ab_not_ab_baud_init()` picked the stage family off `calling_party` alone. The frequency was right by accident (the analogue modem already gets the 2400 Hz CC carrier, which is Tone A); the *timetable* was not. **Which tone a modem transmits follows its role, not the call direction** — V.34 gives Tone A to the answer modem (§11.2.1.2) and Tone B to the call modem (§11.2.1.1), and V.90 keeps both timetables but hands them to the other end of the call, so §9.2.2.1 is §11.2.1.2 word for word with INFO0d/INFO1d for INFO0c/INFO1c and the Tone A transmitter is the side where `calling_party` and `v90_mode` agree (the same predicate `v34rx.c` already used to pick the receive carrier). The correct choreography was therefore already in the tree as the V.34 answer-modem A family, just unreachable. Three fixes in `v34tx.c`: the stage family now routes on the role; the end of the analogue's own L1/L2 goes to `second_a_baud_init()` rather than `pre_info1_a_init()`, because §9.2.2.1.5's probe is only the first of two rounds and jumping to Tone A skipped the §9.2.2.1.6 Tone A/reversal/silence that §9.2.1.1.6 times its Tone B reversal against (the digital modem sat in `SECOND_B` and never sent INFO1d); and `FIRST_A` now waits for the peer's tone to be *detected* as well as its INFO0 received, which is what §9.2.2.1.3 literally says — reversing on `INFO0_OK` alone is only equivalent when the peer's tone is already up, and in V.90 it never is, because §9.2.1.1.1-9.2.1.1.2 have the digital modem start Tone B *after* it receives INFO0a (that third one is gated to V.90: §11.2.1.2.3 says the same, but the V.34 answer modem's receiver sits in `V34_RX_STAGE_TONE_B`, whose detector never publishes `TONE_SEEN`, so requiring it there would deadlock plain V.34). A fourth defect fell out next to them: the digital side's `FIRST_B_SILENCE` recovery branch set `stage = V90_WAIT_TONE_A_REV` without moving `current_getbaud`, and that stage's case lives in the *A* getbaud, so it held Tone B for the rest of the call. The coupled analogue-vs-digital Phase 2 harness in `vpcm_loopback_test.c` now completes in both laws with CRC-clean INFO1d and INFO1a, and runs in `make test` instead of behind `--experimental-v90-info`. **That harness now runs Phase 3 and Phase 4 as well, and does so by default** (2026-08-19): it was skipped with "native V.34 half-duplex startup does not complete over the bare G.711 loopback", which had stopped being true, and it is the only coverage that points our two roles at each other, so the seam it covers had rotted. Three defects, each masked by the next, and all four contract-path variants now pass with CPt and CP demodulated off the wire in **both** laws (an A-law-only oracle used to hand the digital side the CP structure directly, so that law never exercised the receiver at all; it is gone). G.711 is not the constraint (`V34_DUPLEX_G711_SNR` measures 37.3 dB on the actual waveform). **21600 at 2400 baud is deliberately not asserted** -- 9 bits/symbol and an 896-point constellation, the densest V.34 allows, where the result is an acquisition coin flip at ~2% BER. **Live, the rig's channel is the binding constraint and it is measured: 16.8 dB** (mean symbol power 7.22, distance 0.1517 at 3000/9600, where LAPM carries all 300 pattern lines) against the ~37 dB 21600 needs. The peer's own receiver independently selects 9600 for its receive direction, and raising the rig's deliberate -12 dB pad (`HEADROOM=1.0`) changes the measured distance not at all. Open: **choose the rate we ask for from a measured receive SNR** rather than a configured start profile -- the distance-to-grid figure is exactly that measurement. -- `docs/v34_data_mode_rates.md`

- **9600 was never the V.34 ceiling on the live rig -- 14400 runs, and nothing before data mode can tell you that (2026-08-22).** The previous entry's "the rig carries ~9600" was a measurement of a channel nobody had asked to work harder: **every live plain-V.34 call had `ME_V34_BPS=9600` set**, the rate this modem puts in MP is `min(configured start profile, L1/L2 probe projection)`, and the profile was the binding term. The peer's own log in `artifacts/v34-21600-20260822T-c65` says it plainly -- it measured *its* receive direction at `equerr 1593`, chose 14400 for what it would accept from us, and then transmitted **9600, our number**. Asking for more, at 3000 baud (`tools/soak/v34_rate_call.sh`, three calls kept under `artifacts/v34-rate-*`): **14400 -- the peer transmits it, our receiver holds 0.32-0.39 from the lattice for 13 s and 245 payload lines reach the peer's DTE; 16800 -- white (0.63-0.68) from its first window; 21600 -- `NO CARRIER`.** The line measures **18 dB at all three** (the constellation changes, not the channel), which is enough for 4.8 bits/symbol and not 5.6; 16800 failing from the *first* window rather than degrading is the SNR cliff, and 16800 is clean on the loopback at the same symbol rate. **Neither place a rate decision could be taken can see this line.** The Phase-2 L1/L2 probe: pulled out of the c65 recording at t=9.02 s its unoccupied bins read 1.7e-24 -- the rig adds no noise at all, and `if (noise < 1.0f) noise = 1.0f` is the only thing keeping the projection finite -- so it reported 37.9 dB for a data mode that ran at 17.6, because the impairment is signal-proportional and a 21-tone probe on a 150 Hz grid puts its own products back on that grid. The Phase-4 TRN segment, which is what the peer uses (`V34EQU equerr` feeding `V34DATARATE` one line before `txmp bits`): `v34_phase4_trn_measured_rate_n()` implements it, and swept over `V34_DUPLEX_NOISE_DB` at 40/34/30/27/24/20 dB it reads 9.8/8.7/8.4/8.4/11.4/9.8 while the same calls' data mode moves 0.0018 -> 0.0285. It is reading our own Phase-4 convergence: **our Phase-4 TRN symbols sit at ~10 dB on a bearer where our own data mode reaches 31 dB**, the same story as Phase 3's "TRN mean distance to nearest 4-point 0.620". It is therefore logged and never applied (`ME_V34_TRN_RATE=1` applies it, and caps a clean loopback's 9600 down to 4800, which is the point). The one instrument that does see it is the data mode itself, so `Rx - DATA: distance to grid` now also reports the receive SNR, the rate the line will carry (`bits = (snr_db + 13)/6`, calibrated on this one channel) and, when the output is white, says so. **Open, and now the whole of it: closing the loop.** The answer only exists after the rate is committed, so V.34 12.2 rate renegotiation is what turns it into a rate this modem picks itself; until then the rate is `ME_V34_BPS` and the default -- the maximum for the symbol rate -- is wrong on any real line. -- `docs/v34_data_mode_rates.md`

- **Beyond 14400 on the rig: no, and the ceiling is the peer's own transmitter (2026-08-22).** `tools/v34_channel_bound.py` answers the question no in-receiver metric can, because they all rest on the receiver's own decisions: given a recorded tap and the symbols the receiver decided, it fits the **best possible** fractionally-spaced least-squares equalizer -- non-causal, as long as you like, solved exactly rather than adapted -- so its residual bounds every linear receiver. On the 14400 call: what we received measures **19.5 dB** at that bound (161 T/2 taps; 18.7 at 41, 19.2 at 81), **our actual receiver got 18.5** -- within 1 dB of anything achievable -- and **slmodem's own 9600 Hz output, tapped before any resampler, codec or network, measures 21.5 dB**. So the whole rig path costs ~2 dB on top of a source that is already only 21.5, and there is nothing left to win at our end. (The d-modem container writes that pre-interpolation tap unconditionally to `/tmp/dm_from_dsp_9600.raw`; `--rate 9600 --raw16` reads it.) The channel is static, not time-varying -- the same fit over 1024/512/256/128-symbol windows gives 20.0/20.2/20.7/21.7 dB, one number plus each window's overfitting bias -- so a smarter receiver has nothing to chase. Four rig causes tested and all ruled out: **level** (`HEADROOM=1.0` vs 0.25, a 12 dB change: 18.4 vs 18.5 dB), **timing slips** (one in the whole call, against 28 in 290 s on the V.90 soak), **band clipping** (the ZOH loop model and its 4400 Hz lowpass are built but not in the path -- the active one is the 257-tap sinc), and **the upstream resampler kernel** (`DM_UP_TAPS=64` vs 32: no improvement; both knobs now plumbed through `tools/soak/v34_lapm_call.sh`). **Why 16800 cannot fit, arithmetically: the lattice spacing is always 2, so at fixed SNR the distance to the grid scales with constellation power.** 14400 at 3000 baud is power 21.7 at distance 0.35; 16800 is 1.74x the power, so the same 18.5 dB puts it at 0.61 and 0.667 is white -- which is exactly what the live calls show. **The one route left is not SNR-limited and it is ours: 16800 at 3429 baud is 4.9 bits/symbol, the same density as the 14400 that works.** It does not train -- live the peer sets up 3429/1959, reaches `XMITMP` and then `going into retrain in Handshake`, at 16800 and at 9600 alike, so our Phase 4 never completes the MP exchange and there is not even an SNR reading for that symbol rate. 3429 is the same row that is weakest on the loopback (3429/19200 does not train there either) and has been outside `make test`'s asserts since the symbol-rate matrix work. Fixing 3429 is the whole of the remaining route past 14400 here. -- `docs/v34_data_mode_rates.md`

- **21600 live: the ceiling was a 30 Hz notch of our own, inside the receive band (2026-08-22).** The previous two entries said 9600, then 14400, was what this rig could carry, and that the limit was the peer's transmitter. Both were wrong. **Our receive direction now runs 21600 at 3000 baud** (166760 symbols, 0.037 from the lattice, 34.9 dB) and 16800 at 3000 *and* 3429 baud (0.008-0.013, 34.4-34.8 dB); the peer refuses to transmit above 21600 whatever we ask, so the limit is now the far end's. **`v34_update_echo_policy()` puts a 30 Hz notch at our own transmit carrier into the receive path, and chose to do so on carrier *separation*** -- at 3000 baud TX high 2000 Hz against RX low 1800 Hz is 200 Hz apart and passed the `>= 150 Hz` test -- **but the received signal occupies 120 to 3480 Hz, so 2000 Hz is 200 Hz from the middle of it.** A 30 Hz notch is an impulse response of ~266 samples, 114 symbols at 3000 baud, against the 63 symbols the equalizer spans: it cannot be equalized out. Back to back on identical calls, 3000/9600: `ME_V34_ECHO=notch` gives distance 0.139 and **17.2 dB**, no echo filter gives 0.002 and **34.8 dB**. **Two things hid it for months: the notch is applied *after* the RX G.711 tap, so every recording of a live call shows a clean signal and every offline analysis exonerates the wire; and `v34_duplex_test` never runs the engine at all -- it drives `v34_rx()` directly -- so no loopback row could show it.** The 30 dB loopback / 17 dB live gap was the entire symptom and it was blamed on the line. Default is now: transmit carrier inside the receive band -> no echo filter, else the notch as before; `ME_V34_ECHO=none|notch|canceller` forces one. **`tools/v34_channel_bound.py` is what turned the search inward** -- it fits the best possible fractionally-spaced least-squares equalizer to a recorded tap given the receiver's decided symbols and reports the residual on held-out data, bounding every linear receiver, and it reads **38-39 dB on three independent clean calls** where the receiver delivered 17. **Two traps in using it, both of which gave wrong answers first: the carrier must be right to a fraction of a hertz** (0.18 Hz, the gap between 1959 and 3429 baud's exact 1959.18, is 19 degrees across a 1024-symbol window and caps the fit at ~20 dB however good the line is -- it is swept out now), **and the decided symbols are truth only where the call is decoding** (run on a 14400 call sitting at 0.35 from the lattice it reads 19.5 dB on a wire a clean 9600 call reads 39 on -- which is exactly how the previous entry concluded "the ceiling is the peer's transmitter at 21.5 dB", a figure taken from a 14400 call's decisions). **3429 needed a fix of its own**: it alternated pass/fail by rate parity on the loopback in both laws (9600 fail, 12000 pass, 14400 fail, 16800 pass, 19200 fail, 21600 pass), because the T/2 eye-phase chooser fires *inside* 10.1.3.6's supervised PP conditioning -- a stage trained against a known 232-baud sequence with the AGC frozen, so moving the symbol instant part way through invalidates everything after it (PP mean residual 0.192 -> 0.805, TRN then never locks, J never decodes exactly, Phase 3 deadlocks). The chooser now measures during PP and acts after it. Scoped to the *move* not the measurement (suppressing accumulation shifts later window boundaries and cost 3000/21600 u-law 37 errors) and to the window not a vote count (2743 flips just before PP and must keep doing so; two agreeing windows costs 2743/9600 in both laws). `ME_V34_EYE_PP_GUARD=0` restores it, and `ME_V34_EYE_SELECT` now accepts `0` as well as the literal `off`. -- `docs/v34_data_mode_rates.md`

- **V.90 carries the same never-retired notch, and the V.34 fix does not reach it (2026-08-23).** `v34_update_echo_policy()` returns immediately when `g_mod != ME_MOD_V34`, so the plain-V.34 echo fix above does nothing for V.90 -- and V.90 has the defect in a worse form. `v8_result_handler()` puts a 30 Hz notch on **1200 Hz**, our own CC transmit frequency, which is right for Phase 2 (both signals narrowband, 1200 Hz apart, no cost to the 2400 Hz we listen to) and wrong from Phase 3 on, where the upstream is a wideband V.34 signal spanning ~36-3620 Hz at 3200 baud low carrier and 1200 Hz is deep inside it. **Nothing retired it**: `start_v34_training()` disables the notch at 3200 baud (91 Hz separation too narrow), `v8_result_handler()` re-enables it at 1200 Hz for Phase 2, and the only later clear is on the fallback to plain V.34 -- every V.90 soak log in `artifacts/` shows exactly those two notch lines and no third. `v90_retire_phase2_cc_notch()` now clears it at Phase 3; `ME_V34_ECHO=notch` keeps the old behaviour; the wideband NLMS canceller is untouched (gated on `g_mod == ME_MOD_V90`, and the right tool against a broadband PCM echo, which one notch never was). **Worth, over two A/B pairs (`tools/soak/v90_notch_ab.sh`, upstream pumped all call): the upstream delivers 341967 and 340407 bytes to our PTY with the notch retired against 37394 (call dropped at 13 s) and 0 with it left in, and the upstream receiver produces 2906 DATA-bit reports against 311 and none.** So the path runs for the whole call instead of stalling. **It does not fix the upstream decode**: the symbols are white in all four runs (best `sym err` 0.648/none with the notch, 0.580/0.564 without, against 0.667 for symbols unrelated to the lattice) and not one intact `U%07d` line arrives in any of them. Kept because the mechanism is proven in the V.34 path and a notch inside the received band that nothing retires is a defect by inspection -- not because it was measured to fix the upstream. -- `docs/v90_upstream_data_path.md`

- **The V.90 upstream's dominant impairment was our own echo canceller, and the notch fix had only ever run on the first call of a process (2026-08-23).** The entry above retired the Phase 2 CC notch and reported that it did not fix the upstream decode. Both halves of that are now superseded. **(a) `v90_retire_phase2_cc_notch()` guarded itself with a `static bool retired` -- process lifetime, not call lifetime.** `v8_result_handler()` re-arms the 1200 Hz notch on every call, so call 1 retired it and every later call re-armed it and could never retire it again; on this rig the call that reaches data mode is rarely the first. In `artifacts/v90-cap-20260822T130820Z-9600/server.log` the retirement appears once, against call 1, and the call that actually reaches data mode has no retirement line at all -- and ran its whole upstream at **0.139** from the lattice, the same figure the plain-V.34 notch left. `g_notch.active` is already the right once-per-call guard, so the latch is simply gone. **(b) THE BIG ONE: the NLMS echo canceller, unconditional on every V.90 call, was not cancelling an echo -- it was adding one.** It prints its own verdict every 8000 samples and nobody had read it: its effect on the receive RMS oscillates around zero (+0.2 to -0.4 dB, mean nil), and on the batches where the received signal is digital silence it reads **`pre_rms=0 post_rms=106`, `pre_rms=0 post_rms=159`**. A filter that turns silence into RMS 159 is injecting its own transmit-driven misadjustment -- and in V.90 that transmit reference is the downstream PCM, 8.4 dB louder than the upstream. Against a received upstream of RMS ~1240 that pins the receive SNR at **18-22 dB**, while 31200 bit/s at 3200 baud is 9.75 bits/symbol and wants far more, so the canceller was capping the exact quantity it sat in front of. There is no echo to find either: peak normalised TX/RX cross-correlation 0.0068 over lags 0-1024, and a 512-tap least-squares fit removes 0.307% of the receive power -- 512/160000, the bias of the fit itself. **Same shape as the notch and hidden for the same two reasons: it is applied AFTER the RX G.711 tap, so every recording exonerates the wire, and no loopback exercises it because `v34_duplex_test` drives `v34_rx()` directly and never runs the engine.** Now opt-in on V.90 (`ME_V34_ECHO=canceller`). Back to back on the same binary: canceller on -- B1 out-of-sample distance 0.657/0.675, data-mode `sym err` min 0.548/0.617, **0 intact `U%07d` lines**; canceller off -- 0.226/0.226/0.226, min 0.165/0.186/0.165, **399, 0 and 730 intact lines**, the peer's own traffic on our PTY and the first upstream payload this path has delivered. 0.667 is the value for symbols unrelated to the lattice, so with the canceller in, B1 itself was white out of sample. **Open: payload is intermittent** (two of three data-mode calls), median `sym err` still 0.666 -- the eye opens in bursts, and frame-phase lock still does not hold. **Two causes measured and ruled out, so do not re-run them:** the T/3 loop never had the ordinary V.34 path's B1-derived carrier *frequency* seed (the defect that made plain V.34 white above 12000 bit/s), so it is now implemented (`ME_V90_UPSTREAM_B1_FREQ=0` disables) -- and the residual it measures live is **0.0229 deg/symbol, 0.20 Hz** against V.34's fatal 0.1054, reading -0.0001 with the canceller out; and precoding, since V.34 precoder coefficients travel receiver->transmitter and this side only ever builds MP type 0, so a conformant peer transmits unprecoded. -- `docs/v90_upstream_data_path.md`
