# CLAUDE.md

Gotchas and repo-specific knowledge for this project. Kept in sync with `AGENTS.md`; identical apart from this header.

## What this is

A SIP-based V.90/V.92 **digital-side** modem server. An analog client modem dials in over SIP; this software answers, runs the V.90 handshake over G.711 RTP, and bridges the data connection to a PTY.

The RTP payload **is** the DS0 PCM stream the far-end D/A converter sees. Most of the constraints below follow from that one fact.

## Constraints that silently break the modem

1. **Never transcode G.711.** No resampling, VAD/CNG, comfort noise, echo cancellation, or gain/AGC anywhere in the audio path. PCMU/PCMA codewords pass through byte-exact, for V.90, V.91 and V.92 alike. Passthrough is enabled via `PJMEDIA_HAS_PASSTHROUGH_CODECS` in `pj_config_site.h`.
2. **Never "clean up" DSP constants.** Scrambler taps, RRC coefficients, Ucode/µ-law tables and timing thresholds are ITU-spec values. Two scramblers coexist deliberately: downstream uses V.34 GPC (`1 + x^-18 + x^-23`), *not* the answer-modem GPA (`x^-5` tap). Conflating them is the classic silent breakage here — `v90.c:439`.
3. **Sample-rate error is fatal.** `clock_recovery.c` exists because a few ppm of drift destroys the constellation. Don't add buffering that changes sample accounting.
4. **Cite the spec when changing protocol logic.** ITU-T PDFs are in `ITU Docs/`. Reference section numbers in comments and commit messages, as the existing code does.

## Build and run

`make` builds `sip_v90_modem` and the test binaries. `make test` runs the suite (`data_stack_test`, `v42_link_test`, `v34_phase2_decode_test`, `v92_proc_eval_test`, `vpcm_loopback_test --all-tests`). Python harnesses are separate targets: `v32bis-ref-test`, `v32bis-datapump-test`, `v91-serial-pair-test`.

```bash
./sip_v90_modem --sip-server asterisk.net.cryan.nz --username 6001 --password 6001 --pty-link /tmp/v90modem
```

The PTY flag is `--pty-link`, not `--pty`; passing `--pty` is silently ignored and you get the default `/tmp/modem0`.

The automated tests only cover offline and loopback paths — passing them says nothing about hardware interop, which is verified manually against a real analog modem (`docs/v90_hardware_interop.md`).

Adding a source file means updating `SRCS` **and** the relevant `*_OBJS` lists in `makefile`; the test binaries link overlapping subsets, so a new dependency often needs adding in several places.

**The makefile has no header dependencies** (`%.o: %.c` at `makefile:243`, no `-MMD`). Editing a `.h` does not rebuild the `.c` files that include it, so a struct field added or reordered leaves stale objects linked against the old layout — the symptom is impossible values at runtime, not a link error. `rm` the affected `.o` files (or `make clean`) after touching any header.

**Commit straight to `main`.** This is a single-maintainer repo with a linear history; do not open a feature branch for a change unless asked. (Agent defaults often say to branch off the default branch — that default does not apply here.)

## Platform (macOS Apple Silicon)

- SpanDSP 3.0 builds from source in `spandsp-master/`. Do not substitute a system spandsp.
- `make` prefers the in-repo `pjproject/` tree when present, falling back to Homebrew.
- Both vendored trees are host-specific; `make` auto-`distclean`s and reconfigures when OS/arch changes.
- Override `ARCH_SUFFIX` only if linking a Homebrew pjproject with a different suffix: `ls "$(brew --prefix)/lib"/libpj-*.a | sed 's/.*libpj-//' | sed 's/\.a//'`

## Orientation

Layering that isn't obvious from filenames:

- `vpcm_*.c` is the shared V.PCM-family layer (CP helpers, G.711 stream, session and coupled-training plumbing) sitting under both the V.90 and V.92 paths. Protocol fixes usually belong here, not duplicated into `v90.c` and the `v92_*` modules.
- Not every decoder is live. `p3_demod.c` *is* — via `v90_cp_live.c` and `v92_p3_rx.c`. But `v34_phase2_decode.c`, `v34_info_decode.c`, `v8bis_decode.c`, `phase12_decode.c`, `v92_short_phase*_decode.c` and `v92_anspcm_decode.c` are absent from `SRCS` and reachable only from `vpcm_decode` and the test harnesses. Check `SRCS` in `makefile` before assuming a change affects real calls.
- `*_rrc.h`, `*_godard.h` and `v34_*_tables.h` are generated coefficient tables. Data, not hand-editable code.
- The Eicon Diva Server card work — the ADSP-2181 emulator, the MIPS firmware harness, the DIAL/INFO/V90D investigation tools and their 69-session analysis log — now lives in its own project, `../modem-dsp-emu`. It shares no code with this one: it runs the card's shipped firmware under emulation, rather than implementing the spec. `tools/cx_at.py` and `docs/courier_firmware_analysis.md` stayed here, and that project references them.
- `tools/` holds Python analysis and replay scripts; `captures/` and `artifacts/` hold recorded line audio and run outputs from hardware sessions.

Each module's header comment states its role and the spec sections it implements — read that before the `.c`.

- **The V.34 symbol-rate matrix was never run, and four defects were hiding behind 2400 baud (2026-08-21).** `v34_duplex_test` has always taken `<baud> <bps> <ulaw|alaw>`, but only 2400 was ever exercised; run across all six V.34 rates, every other rate timed out at 60 s with nothing trained. At 9600 bit/s it now trains **11 of the 12 rows and recovers payload without error on 10**, and `make test` asserts those ten (`make v34-matrix-test` runs all twelve without stopping at the first failure). Four defects, each hiding the next. (a) **The answerer's §11.3.1.2.6 J-wait bound was a flat 1000 ms**, which no conformant call modem can finish Phase 3 inside — S, S-bar, PP, 2048T of TRN and J exceed it at every symbol rate — so the interop escape fired on the *normal* path: the answerer abandoned J while the caller was still in TRN and ran ahead into Phase 4, leaving the caller waiting in J for an S that had already gone by. Now 4000 ms (`V34_J_WAIT_MAX_MS`). (b) **The receiver ran 2800 baud 1.56% off the symbol rate.** The T/2 accumulator advance is samples-per-symbol in units of 1/192 of a sample, and 2800 is the one rate whose value (192*20/7 = 548.57) is not a whole number of coefficient sets; the table wrote **189** in place of 192 for that row *alone* to force an integer. The remainder is now carried; the five exact rates are bit-identical. (c) **Phase 4 CMA never stopped** — its 512T bound is keyed on `phase4_trn_after_j`, which only advances once J' has been seen. It now stands down once the level estimate settles. (d) **Nothing ever chose which of the two T/2 outputs per symbol was the eye centre.** The band-edge detector recovers the symbol *rate* and pulls the phase within a T/2 interval but cannot resolve that ambiguity; it was settled by how many T/2 intervals had been generated since the receiver started, and a single ±1 correction from the timing loop can insert or delete one and flip it for the whole call. Sweeping a deliberate offset across a whole symbol on a bit-exact linear bearer, normalised distance to the nearest 4-point symbol through Phase 4: **2400 — offset 0: 0.384, one T/2 away: 0.590; 3200 — offset 0: 0.595 (the worst point of the entire sweep), one T/2 away: 0.293.** The receiver had been sampling 3200-baud Phase 4 *at the eye crossing*, and which way a call landed was a coin flip on sample counts — which is why the failures looked like thin margin and why every earlier change reshuffled which rows passed rather than growing the set. S, S-bar, PP, TRN and MP are all constant modulus, so the eye centre is where the equalized output is largest: both phases are now evaluated over 256 symbols during primary training and the larger taken, with a 1.05 margin, a minimum magnitude so the decision is never taken on §11.3.1.2.4's silence, and a flip cap. Parameters were chosen over 24 rows (both laws at 4800 *and* 9600) so as not to fit the twelve `make test` asserts. Open: 3429 u-law does not train; 3000 u-law trains with 136 payload errors. **Two metrics here are traps and both were believed for a while: 4th-power coherence over the Phase 4 TRN dump reads 0.39–0.47 whether the call completes with zero errors or never trains, and the MP-stage `[EQ]` decision error has its target angle integrated from the *received* dibit, so it measures constellation tightness rather than decode correctness (3429 reads 0.048 and 2800 0.042 while neither trains). What is trustworthy: ground truth against the transmitter's own symbols (`V34_P4TRN_TX_DUMP`/`V34_P4TRN_RX_DUMP` + `tools/v34_trn_ground_truth.py`), and sweeping the sampling instant for the minimum — which is what found (d).** Diagnostics, all opt-in and all caching their getenv: `V34_P3TRN_SYM_DUMP`/`V34_P4TRN_SYM_DUMP` (symbol, line power, tap energy, main tap, sampling phase), `V34_MP_TX_BITS`, `V34_TRACE`, `V34_DUPLEX_LOG`, `V34_DUPLEX_TXRMS`, and `V34_DUPLEX_LINEAR` to bypass G.711 and so attribute a defect to the bearer or exonerate it. — `docs/v34_spec_gap.md` item 5.

- **Upstream payload now arrives (2026-08-20).** The lottery was a *two-dimensional* frame-phase ambiguity, not one: B1 does not tell us the peer's superframe counter, and its end pins the position *within* the data frame only if B1 ends exactly where we think. Sweeping the seven superframe phases alone enumerated cleanly on a live call and found nothing; sweeping the **(superframe, data-frame) pair** — p×j = 112 candidates at a 0.4 s window, under a minute — locks, applied by the decoder at its own frame boundary so a step never disturbs alignment. Live at 9600 upstream with the peer trickling 200 B/s: **downstream 38830/39025 lines 99.5% clean, upstream 1329 pattern lines in sequence with one missing** — the peer's actual data (`U0000500`, `U0000501`, … unbroken) on our PTY for the first time. Across five consecutive calls the sweep locked six times (0, 1, 2, 35, 102, 128 steps; 78–100% ones) and three delivered payload. A lock is released and re-swept when the ones-fraction falls back. **Open:** a lock holds ~27 s and then decays as the Gardner slip count jumps (7→12 in a few seconds), so holding a lock — not finding one — is now the problem. Note the byte-level "% clean" figures understate results badly; they count the garbage emitted while unlocked, so the *line* counts are the honest measure. Timing recovery itself is `v34_gardner.h` + `v34_gardner_test` (S-curve, acquisition, 50 ppm tracking, quiescence) — and in this receiver the matched filter is the adaptive FSE, so the detector reads the equalizer output, not the fixed RRC. — `docs/v90_upstream_data_path.md`.
- **The upstream slip carries a carrier step (2026-08-21).** The peer's slips are now *measured* rather than inferred: `tools/measure_timing_slips.py` reads the transmitter's symbol epoch off a recorded tap, out of the phase of the symbol-rate line in the squared analytic envelope, and one 8 kHz sample moves it by exactly 360 x baud/8000 degrees. On `artifacts/dmodem-soak-0821-rounds/round1` the peer steps by one sample **28 times in 290 s**, net +7.2 ppm, in bursts of three a second apart -- while the RTP is unbroken across every one (21365 packets, no loss, no timestamp jump, media clock within 4 ppm), so the slips are in the peer's audio generation, not the transport. The receiver had been reporting **81** corrections against those 28 events. Four defects, each hiding the next. (a) **The slip search span was wider than the thing it searched.** The lattice score is periodic in one symbol -- three samples at T/3 -- so +/-3 samples offered every minimum twice, once a whole symbol away, and the argmin chose on noise: 46 of 81 corrections were the far copy (36 of them "+2.67" = -0.33 plus a symbol), each moving the shell decoder within the data frame, which the frame-phase sweep cannot undo because it searches frame labels rather than single symbols. Now the half symbol either side, in sixths -- a slip is 1.2 T/3 samples at 3200 baud and a thirds grid has no point within 0.13 of it. (b) **A slip is a passband delay, so it comes with a rotation.** The T/3 ring holds baseband mixed on the absolute sample count, so reading D samples on recovers the right sample *rotated by -wD* -- 82 degrees per sample at 3200 baud low carrier. The search corrected the delay and left the rotation, which is exactly why it kept reporting a flat profile at 0.65 with nothing to choose between candidates: the right instant was in the list and still did not fit the lattice. It also explains the "lottery" -- 82 degrees is near enough to 90, which V.34's differential mapping makes harmless, that the fourth-power estimator sometimes recovered a call unaided. The scorer now derotates by the carrier loop's standing phase (which it never did, so it had been scoring a signal the slicer does not see) and by the offset's implied phase, and an adopted offset carries its rotation into the loop. (c) **Everything adaptive gated on a 256-symbol average**, so the DD-LMS adapted hard onto wrong decisions for ~100 symbols after each slip and walked off the very filter the search needs; a 1/16 estimate now gates the LMS, timing and carrier loops, and the search runs after 48 symbols off the constellation rather than 240. (d) **The frame-phase sweep could not return to its own best candidate** -- it recorded absolute (super_frame, data_frame) pairs, which are free-running counters, so writing one back at a later boundary lands elsewhere; the phase is now a relative shift with an accumulated position that names the candidate. An equalizer restore also reset the sweep counter, and restores fire every 375 ms, so on round1 the sweep never passed step 1 of 112 in five minutes. **Worth:** symbols on the lattice **35.8% -> 60.1%** of the call and the permanent collapse is gone (68 s clean, then white for 145 s with the wire provably quiet; now recovers in 20 s and runs 73 s clean), with real pattern lines reaching the PTY in bursts. **Open:** frame-phase lock still does not hold -- 60% of the call has an open eye and only a few percent is framed right. The release rule cannot be right on a line carrying data: the soak pattern is mostly digits, which through V.14 read 30-40% ones, so a correct decode looks like noise to a rule that releases below 70%. Measured on the one stretch that provably carries payload, the V.14 metric reads 32% at 1.4x -- honest, and about a sixth of the lines. `v90_upstream_replay` reproduces all of it in 75 s. -- `docs/v90_upstream_data_path.md`
- **The upstream lock metric could not see a correct decode of real data (2026-08-21).** **5217 pattern lines off the peer where the same recording gave 14**, 5129 of the gaps between them exact multiples of the 90-bit line -- runs of its actual traffic. The frame-phase lock was released whenever the descrambled stream read under 70% ones, which is right for an idle DTE and exactly wrong for one that is sending: the soak pattern is mostly digits, `'0'` is 0x30, and LSB-first between a zero start bit and a one stop bit that is three ones in ten, so a *perfect* decode reads 30-40% ones. The receiver was finding the phase, decoding correctly, and discarding the lock the moment the peer said anything -- which is what "a lock holds about half a second" had always been. The evidence needed was already computed and discarded: §9.6.3.3 builds the shell index r0 from the ring indices of a mapping frame's eight 2D symbols and the transmitter's construction bounds it to k bits, so an r0 that does not fit cannot have come from a correctly grouped frame -- a frame-phase check that owes nothing to the content. `bitstream_put()` truncates silently, so nothing had looked. Measured over round1: correct-phase windows read 0% in 194 of 202 and never above 3%, wrong-phase windows 3% or more in 92 of every 100. A standing lock is now judged on that (falling back on the marks only where k is zero), and the sweep ranks candidates by it first. **Read line counts, not the ones fraction, from here on** -- it was the right instrument only while the peer was idle. -- `docs/v90_upstream_data_path.md`

Phase 4 (§9.4) does not exist: the engine logs the DIL measurement and the constellation it implies, then hangs up (`ME_V90_ANALOGUE_HOLD=1` keeps the call up for capture). `v90_analogue_rx_test` in `make test` runs the receive path against `artifacts/eicon-digital-downstream/` — the only downstream here we did not generate — reading Sd 64 reps, S̄d 8, TRN1d 30000T and 13–14 CRC-valid Jd frames, then driving the transmitter to Phase 4 off that real signal. **Two conventions the fixture caught, both invisible to loopback: Sd's zero slots must match on level, not codeword** (a working modem sends +0 in every zero slot, and since those slots match Sd and S̄d equally, counting them hides the §9.3.2.4 transition entirely), **and TRN1d is not differentially encoded** — §8.4.5 puts the scrambler output straight on the sign, and only Jd adds §8.4.2's differential encoder; decoding TRN1d differentially yields a clean stream of zeros and truncates it. **Live against the Eicon card under emulation (2026-08-10) the analogue side now completes Phase 2 and drives the card onto its V.90 page** (`INFO_RX complete=1`, `bootpage 7 -> 14 V.90 DPCM`). Three fixes got there, each found by a call: §9.2.2.1.8 — the analogue modem transmits **Tone A** after L1/L2 and answers with INFO1a only after INFO1d (SpanDSP took the V.34 call-modem branch and sent INFO1a immediately, which deadlocks, because §9.2.1.1.7 has the digital modem waiting to detect Tone A before it sends INFO1d); this card **never sends INFO1d at all** and waits for INFO1a, whose bits 37:39 pick its V.90 page, so `ME_V90_ANALOGUE_INFO1D_TIMEOUT=info1a` sends it anyway (opt-in — it is not one of §9.2.2.2.4's two responses, and the conformant INFOMARKSa *replaces* the Tone A the peer wants); and INFO1a is now repeated as a §8.2.3.1 group (4 by default, `ME_V90_ANALOGUE_INFO1A_REPEATS`) exactly as the digital side already repeats INFO1d. It then stops: the card enters page 14 and transmits no Sd. **That is most likely still ours** — the same card under the same emulation has reached V.90 data mode against two real analogue modems, needing neither workaround, and §9.3.1.1-9.3.1.3 make Sd conditional on the digital modem *detecting Ja*, which our transmitter has no foreign grader for. **The §9.2.2.1.3-9.2.2.1.6 tone choreography is now fixed** (2026-08-10): the analogue role was running SpanDSP's V.34 *call modem* tone stages, because `initial_ab_not_ab_baud_init()` picked the stage family off `calling_party` alone. The frequency was right by accident (the analogue modem already gets the 2400 Hz CC carrier, which is Tone A); the *timetable* was not. **Which tone a modem transmits follows its role, not the call direction** — V.34 gives Tone A to the answer modem (§11.2.1.2) and Tone B to the call modem (§11.2.1.1), and V.90 keeps both timetables but hands them to the other end of the call, so §9.2.2.1 is §11.2.1.2 word for word with INFO0d/INFO1d for INFO0c/INFO1c and the Tone A transmitter is the side where `calling_party` and `v90_mode` agree (the same predicate `v34rx.c` already used to pick the receive carrier). The correct choreography was therefore already in the tree as the V.34 answer-modem A family, just unreachable. Three fixes in `v34tx.c`: the stage family now routes on the role; the end of the analogue's own L1/L2 goes to `second_a_baud_init()` rather than `pre_info1_a_init()`, because §9.2.2.1.5's probe is only the first of two rounds and jumping to Tone A skipped the §9.2.2.1.6 Tone A/reversal/silence that §9.2.1.1.6 times its Tone B reversal against (the digital modem sat in `SECOND_B` and never sent INFO1d); and `FIRST_A` now waits for the peer's tone to be *detected* as well as its INFO0 received, which is what §9.2.2.1.3 literally says — reversing on `INFO0_OK` alone is only equivalent when the peer's tone is already up, and in V.90 it never is, because §9.2.1.1.1-9.2.1.1.2 have the digital modem start Tone B *after* it receives INFO0a (that third one is gated to V.90: §11.2.1.2.3 says the same, but the V.34 answer modem's receiver sits in `V34_RX_STAGE_TONE_B`, whose detector never publishes `TONE_SEEN`, so requiring it there would deadlock plain V.34). A fourth defect fell out next to them: the digital side's `FIRST_B_SILENCE` recovery branch set `stage = V90_WAIT_TONE_A_REV` without moving `current_getbaud`, and that stage's case lives in the *A* getbaud, so it held Tone B for the rest of the call. The coupled analogue-vs-digital Phase 2 harness in `vpcm_loopback_test.c` now completes in both laws with CRC-clean INFO1d and INFO1a, and runs in `make test` instead of behind `--experimental-v90-info`. **That harness now runs Phase 3 and Phase 4 as well, and does so by default** (2026-08-19): it was skipped with "native V.34 half-duplex startup does not complete over the bare G.711 loopback", which had stopped being true, and it is the only coverage that points our two roles at each other, so the seam it covers had rotted. Three defects, each masked by the next, and all four contract-path variants now pass with CPt and CP demodulated off the wire in **both** laws (an A-law-only oracle used to hand the digital side the CP structure directly, so that law never exercised the receiver at all; it is gone). (a) The harness hardcoded the upstream carrier `high` while the digital receiver negotiated `low` -- the *same* defect as (a) above, still present here because this path never exercised the live fix; it now derives it from the received INFO1d. (b) **`phase3_abs_bits` copied the +45 degree bias from the differential decode beside it.** That bias is right for `ang3`, a phase *difference*, which for 4-point DPSK clusters on 0/90/180/270; `ang1` is an ABSOLUTE angle and the 4-point training constellation sits at 45/135/225/315, so the same bias put the `>>30` boundaries **onto the constellation points** and every direct-mapped 10.1.3.8 TRN symbol sliced to a coin flip -- measured against a known transmitter, 117/200 with the bias and 200/200 without. TRN descrambling went from 54% ones (under the 70% lock gate, so Phase 3 never locked) to 98%. Only the Phase 3 sites change: the Phase 4 `abs_bits` sites feed the absolute-domain MP decode where the constellation lands elsewhere, and unbiasing them regressed `v34_duplex_test` from 0 to 84282 bit errors. (c) **The CP hypothesis was searched when it is exactly known.** 9.4 CP is differentially encoded and a differential decode has no carrier-phase ambiguity: 10.1.3.3 advances the point index by the dibit and `training_constellation_4` is ordered so an increasing index rotates clockwise, so the recovered dibit is always the *negation* of the transmitted one -- `map_phase4_raw_bits()` hypothesis 8, fixed by the encoder and the table, not the channel (offline it recovers the frame 972/972 bits). The search was instead seeded from the Phase 3 TRN/J lock hint, which is measured on directly-mapped TRN and so describes the ABSOLUTE-domain rotation; the lock wandered over hypotheses 5, 9, 18, 21, 22, 23 and never settled. Related: the MP retry rotation is now suppressed for V.90 CP, where domain, tap and bit order are all already fixed by spec -- rotating off them cannot find a better setting, and A-law proved it by locking the correct hypothesis on an 18/18 preamble and then rotating to `ord=b1,b0` and `tap=17`, after which nothing validated for the rest of the call. **Measured live against the Eicon card under emulation (run 55, 2026-08-10) the results are larger than loopback suggested.** Phase 2 completes in 2823 ms with **no environment workarounds at all** (it needed all three of `ME_V90_ANALOGUE_INFO1D_TIMEOUT=info1a`, `ME_V90_ANALOGUE_INFO1A_REPEATS=40` and `ME_V90_ANALOGUE_INFO1D_WAIT_MS=12000`, and took 7203 ms). **The card sends INFO1d** -- 109 bits, CRC 0, contents a sane line probe (3200 baud low carrier 31200 bps, 2400 high 24000 bps). "This card never sends INFO1d at all" was recorded as a property of the card and was ours: 9.2.1.1.7 waits to detect Tone A after the L1/L2 it expects, and the analogue side was never transmitting the 9.2.2.1.6 Tone A. So workarounds 2 and 3 in `docs/v90_analogue_role.md` are obsolete, and `INFO1A_REPEATS=40` is now *harmful* -- its 4801 ms of repeats push Phase 3 from 7.4 s to 11.8 s, past the card's page-14 dwell. The card also gets further: `0x0060 -> 0x0062 -> 0x0068 -> 0x0070 -> 0x0072 -> 0x0074 -> 0x0076 -> 0x007a` with `DI_control=rx0_valid`, where it used to stall at `0x0074`. **Two further bugs, both ours, then had it transmitting a full Phase 3 downstream.** (a) The upstream carrier was hardcoded `high` in `prepare_v90_analogue_phase3_locked()`, and `s_not_s_baud_init()`'s `calling_party` branch excluded `v90_mode` so power/pre-emphasis fell to the "no INFO1 received" default. INFO1d is V.34's INFO1c (Table 9) and V.34 10.1.2.3.4 has it describe the *answer* modem's transmitter -- us, per 9.2.2.1.9. The card asks for the **low** carrier at 3200 baud, so our whole Phase 3 sat at 1920 Hz against the 1829 Hz it was tuned to; its Ja detector found nothing, 9.3.1.3 never fired, and it transmitted 4.5 s of pure `0xFF` (RMS 0). Both now read INFO1d. With that fixed it emits a textbook downstream -- `Sd 64 reps at W_UCODE=64, S-bar-d 8 reps, TRN1d 30005T (3750.6 ms), then Jd` -- and its states run past `0x007a` for the first time to `0x00b0`, reporting `SNRatio 31.5 dB` on our upstream. (b) We still could not see it: `v90_analogue_rx.c` hunted Sd only at W = 16 + the U_INFO *we announced*. **The card does not honour it** -- told 78 it sends W = 64, told 48 it sends W = 35, and both in-tree Eicon fixtures also run at W = 64. Acquisition now learns W from the wire structurally (four W slots at one non-zero level, signs + + - -, two zero slots), and TRN1d's level is derived as W - 16 since 8.4.4/8.4.5 lock them 16 apart. Live: `Sd 64 reps, S-bar-d 8 reps, TRN1d 24000T+`, with Ja ending on the 9.3.2.4 transition. **Remaining: the TRN1d -> Jd seam on a live stream** -- it oscillates and no Jd frame validates, so 9.3.2.6's S is never sent. The file fixture decodes 13-14 CRC-valid Jd frames, so the difference is live RTP; a single lost or substituted sample desynchronises the 5.3 descrambler and this is exactly where that shows. `ME_V90_ANALOGUE_HOLD=1` also holds the call on the 9.3.2 deadline path now, which is the path a capture most needs held. `SIP_FORCE_PCMU=1` is required for these runs: a transcoded DS0 cannot carry Phase 3. Default is unchanged. **Phase 4 (§9.4) now exists** -- `v90_analogue_phase4.c` is the 9.4.2 receiver (Ri, the R-bar-i transition, TRN2d, MP) and the 8.5.2 CP builder; the transmit stages live in `v90_analogue_tx.c` because 8.5.2 sends CP through J's modulation. B1 (9.4.2.5) does not: it needs the data-mode mapper the analogue role lacks, so the transmitter holds silence there. Live, the card acquired Ri and stayed in it for thirty seconds -- 79,979 runs of exactly three signs, never R-bar-i -- and 9.4.1.2 sends R-bar-i only "after receiving a CPt sequence". **That was ours, and provable offline: `v90_analogue_phase4_build_cp()` set Sr = 1 believing it the minimum, but 5.4.5 says "when Sr = 0, spectral shaping is disabled".** Sr = 1 means S = 5, and everything downstream assumed S = 6: CPt's K became (drn+8)-5 = 25 against Table 17's ceiling of 24, so no digital modem can build the TRN2d mapper 8.6.5 needs; and CP's K exceeded log2(prod(Mi)) because `vpcm_cp_drn_to_k()` was hardcoded to D-6, breaking 5.4.3. Feeding the builder's own output to this tree's *digital* half (`v90_set_phase4_cp()`) rejects it at every attenuation from 0 to 11.77 dB and every constellation from 9 to 65 Ucodes; at Sr = 0 all are accepted. The 11.77 dB pad the old note blamed was a red herring. The fix is Sr-awareness end to end rather than a new constant, since all four values are legal: `vpcm_cp_drn_to_k_sr()`, `v90_dil_measure_plan_rate_sr()` (the plan now carries the Sr and K its drn means), `build_cp(m, law, sr, ld, ...)` deriving CPt's rate from **K** (min(K_CP, 24)) rather than clamping the field, the new `v90_analogue_phase4_cp_k()` as the Table 17 / 5.4.3 check both frames are run through before they leave, the Sr = 0 demap and generate paths (`v90_demap_mapped_frame()` and `v90_map_scrambled_frame()`, both already live), and ld clamped to Jd bits 49:50 at the handover. Default `ME_V90_ANALOGUE_SR=0` -- the only value needing nothing agreed with the far end. `v90_analogue_rx_test` now runs Phase 4 receive at all four Sr and puts every built CPt/CP through `v90_set_phase4_cp()`; the old test asserted `Sr >= 1` beside the code that set it. **Live (run 79, 2026-08-11): R-bar-i follows.** The card's Ri ran 2568T of Ucode 22 in + + + - - -, then exactly four repetitions of - - - + + + (24T, 9.4.1.2 to the symbol), then a mapped stream -- against thirty seconds of unbroken Ri before the fix. The refusal was the K, as the offline check said. **The card's TRN2d still does not demap, but the reason is now measured, and it is neither of the two the last session proposed** (2026-08-19). 30 s of that downstream is kept as `artifacts/eicon-phase4-downstream/` -- the first foreign Phase 4 downstream in this tree -- and `v90_analogue_rx_test` now runs against it, which it did not before. **Our six-symbol grid is right**: the receiver puts TRN2d's first symbol at sample 6135, and an independent scan of Ri's sign pattern agrees (the `+ + + - - -` grid reverses after 2544T and runs 24 more). `v90_analogue_phase4_r_symbols()` reports Ri as 2556T only because the reversal detector consumes two of R-bar-i's four repetitions before firing; the TRN2d start is unaffected, and the test pins the start rather than the counter. **And nothing is outside the constellation**: the demap failure counter had one bucket and a comment asserting it meant exactly that, but `v90_demap_mapped_frame()` also returns 0 when 5.4.3's modulus value needs more than K bits -- which is not a statement about any symbol, and which also fires for a locally over-wide CP (enable every Ucode and prod(Mi) is 128^6, far over any legal K). Split by cause, it is **out-of-constellation 0 and modulus overflow on every one of the 38977 frames**. The "13%" was measuring the wrong thing. **That conclusion was wrong, and the real cause is ours (2026-08-19, later).** Reading run 79's TRN2d back through the 5.4.3 modulus decoder over the data constellation the analogue side actually chose that call (`Mi = 39 39 37 39 39 39`, `docs/v90_analogue_role.md`) gives modulus values reaching **2^31.6**, median **2^31.3** — 99.6% of frames exceed 2^24. The card mapped TRN2d at **K ≈ 31, the data K, not CPt's K = 24**. The earlier "39^6 needs K=32, not scrambled ones, question for the firmware" read the same overflow through a placeholder CPt (`drn=12`, all Ucodes) and mistook it for a card mapper of the card's own. It is not: 8.6.5 has the digital modem take K from the constellation CPt hands it, and `v90_analogue_phase4_build_cp()` built CPt from the **full** data masks (prod(Mi) ~ 2^31) while only relabelling `drn` to declare K = 24 — so the offer *was* K = 31 whatever the field said, and the card mapped it faithfully. **Fixed by reducing CPt to a genuine subset** whose `prod(Mi)` is commensurate with K ≤ 24, dropping the lowest-amplitude points first (which keeps 8.5.2's "CP no more than 3 dB above CPt" on the safe side — the *opposite* of run 86's power-thinning, which dropped high points and fell the card back to Phase 3). `v90_analogue_rx_test` now asserts CPt is a subset of CP with mask capacity `prod(Mi) < 2^25`, and the coupled loopback still reaches data mode in both laws. Live re-verification against the card — it should now map TRN2d at K = 24 and let MP through — is the open confirmation, and needs the `../modem-dsp-emu` rig. The run 79 capture predates the fix and is kept as the record of the K = 31 TRN2d the old CPt provoked. Run 77 also exposed a reporting hole, since fixed: a measurement that yields no constellation at the 3-sigma margin logged nothing at all, because "Phase 4 cannot start" was one-shot on Phase 3 completion, which fires a receive batch before the handover. `v90_dil_measure_plan_rate()` returning false rather than backing off to a floor is now the open item that cost that call. — `docs/v90_analogue_role.md`.
- **TRN1d length is NOT why the Courier ignores our Jd — tested live 2026-08-12 and disproven.** A working V.90 digital modem (the Eicon card, `artifacts/eicon-digital-downstream/`) transmits **30000T / 3750 ms** of TRN1d against our 2496T / 312 ms, which made it the leading suspect. `ME_V90_TRN1D_SYMBOLS` already allows up to 32000 (the "clamp <=16000 blocks testing" note was stale). At 30000T the Courier retrains *sooner*: its deadline is §9.3.2.7's "within 4500 ms from the end of Ja", which TRN1d does not move, so 3750 ms of TRN1d leaves Jd only **491 ms** of airtime instead of **4764 ms**. At the default length it receives 4.7 s of Jd and retrains anyway — the objection is in Jd's content or framing, not in training length. Do not adopt 30000T — `docs/v90_phase3_s_and_rbs_false_positive.md` §21.
- **Receive path against a foreign downstream — Phase 3 reads, DIL does not** — every other receive test is fed by our own transmitter, so a wrong-but-self-consistent assumption is invisible to it. `make eicon-rx-test` points the analogue-side decoders at the Eicon card's downstream. Sd, S̄d, TRN1d (30005T) and Jd now decode at the offsets an independent segmentation puts them at, on both fixtures. **DIL is two different jobs — do not conflate them.** On the analogue side the descriptor is an *input*: §8.4.1 sends it to the digital modem in Ja and §9.3.2.9 has the analogue modem "receive the DIL sequence it requested", so the receiver measures impairment rather than recovering anything, and §9.3.2.10 lets it stop once it has "enough". `v90_dil_measure.c` does that job — from **half a pass** it recovers a 3 dB pad and the RBS slot exactly, then turns what arrived into Ci/Mi/drn/rate under a measured noise margin and §8.5.2's Table 15 power cap. Noise thins the constellation from the bottom of the ladder (G.711's levels sit closest together there), §8.5.2 from the top (largest levels dominate the power sum), and measured it is the **combination** that moves the rate — either alone usually costs constellation and no bit/s. Two traps are documented and worth knowing before authoring a DIL descriptor: LTP must be coprime with 6 or an interval goes unprobed, and alignment must never be searched blindly. See `docs/v90_constellation_selection.md`. Never attempt blind alignment: G.711 is self-similar across chords (Ucodes u and u+16 differ by exactly 2×), so a one-Ucode-per-segment ladder repeats its shape 16 segments later and no scale-invariant score separates them; §9.3.2.8-9 means the receiver searches a window instead, hence the from/span API. `v90_dil_rx.c` solves the *other* job, recovering a descriptor from someone else's capture. Its acquisition no longer needs the cycle twice (a single pass decodes exactly, pinned by `V.90 DIL decoded from a single pass`), but the card's low-Ucode region still defeats it: at a uniform 66T segmentation 51 of 239 segments carry three Ucodes where §8.4.1 allows two, most likely because Hc is per-chord and the ladder crosses chords. A tool limitation, not a modem one — `docs/eicon_downstream_comparison.md`, Finding 5.

- **Plain V.34 to data is blocked in the peer, not here (2026-08-21).** Running `ME_MODE=v34 ME_DATA_FRAMING=lapm` against the d-modem rig (`tools/soak/v34_lapm_call.sh`) found and fixed a real defect of ours first: **§11.2.1.2.6's post-L2 Tone A phase reversal is conditional on Tone B having been *detected*, and we sent it off the end of our own L2** -- §11.2.1.1.3 keeps the call modem silent from its first Tone B reversal until it has received L1/L2 and §11.2.1.1.5 raises Tone B only after that, so it is not listening when our L2 ends. Measured on the taps: our reversal at 7565 ms, its Tone B at 7630 ms. `V34_TX_STAGE_POST_L2_WAIT_TONE_B` now holds Tone A until Tone B is seen; before the fix our receiver read the peer's INFO0c repeats as its L1/L2 probe and "analysed" them. **The remaining blocker is the peer's shipped SmartLink DSP.** It declares `Repeated info0 is detected` 20 ms after entering `TX_PHASE2_CALL` on *every* call -- while our transmitter is silent, and with a DPSK sync search over our own transmit tap finding exactly the two INFO0a frames we meant to send and no others -- and the §11.2.2.1.1 recovery it enters has one exit, receiving an INFO0a, which `TX_PHASE1_CALL` reads as a repeat 60 ms later, looping off `Tone AB detected ending errorrecovery` until it retrains. All three possible answers were measured and all three fail (`ME_V34_INFO0_RETRY=ack|noack|none`: livelock, livelock -- so the check is repetition, not bit 28 -- and never leaving `DET_SYNC`). Reproduced on two peer binaries. The same peer raises the identical flag in its **answer** role and recovers cleanly, which is why V.90, where §9.2.2 hands the analogue modem the V.34 *answer* modem's timetable, reaches data mode on this rig and plain V.34 never has. The way through is to give the peer that role by originating (`tools/soak/v34_originate_call.sh`), which needs inbound support the rig does not have: d-modem is spawned *by* the dial, sets `register_on_acc_add = false`, and has no `on_incoming_call`/`pjsua_call_answer` at all. **Read the two G.711 taps against each other with `tools/v34_phase2_timeline.py`, never the two modems' logs** -- their clocks differ by a per-call offset, and getting that offset wrong cost this investigation a round chasing a probe overhang that does not exist. Then the other direction was opened up and it is dead too: d-modem on tower now has an inbound path (listen mode keyed on the empty `argv[1]` slmodemd's `socket_start()` passes after ATA, plus `DM_TX_GAIN`/`DM_RX_GAIN`, all defaulting to no-ops with the outbound path re-verified unchanged), and with the peer answering it never leaves `V8_ANS_SEND_ANSAM` -- we hear its `ANSam/`, send CM eleven times and time out waiting for JM, with level measured out at +15.6 dB into its DSP and the `AT+MS` configuration ruled out. **Both of the peer's roles are blocked, each in a path its firmware never exercises**; the one pairing it completes is the one V.90 creates -- SIP caller, V.8 caller, V.34 *answer* modem -- which plain V.34 cannot reproduce because it ties the role to the call direction. -- `docs/v34_plain_phase2_call_role.md`
