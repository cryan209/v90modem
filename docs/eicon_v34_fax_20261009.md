# Eicon V.34 fax: pages in both directions, 9 October 2026

Follow-up to [eicon_v34_fax_20261008.md](eicon_v34_fax_20261008.md), which
left every page we sent the Eicon Diva BRI card failing its HDLC FCS check
even though an independent offline decoder recovered the whole page from the
card's own received audio.

**Result: V.34 half-duplex fax now carries pages both ways between this modem
and the Diva card, with V.34 as the transport and no fallback.** Every page
below is compared pixel for pixel against the 1728 x 2292 source raster and
differs in zero pixels.

2292 source rows match exactly.

## The reference that found it: the card faxing itself

The decisive measurement was the card's **own** V.34 half-duplex source
transmission. The spare `/dev/ttyds5` (controller 1, `ATX4`, origination
7911) sent a page to 7910 with the Diva's internal Class 2 T.30, while HylaFAX
received on ttyds3/4 and `divactrl mlog -o -c 1 -A1` traced the sender's
B-channel audio. Two notes for anyone repeating it:

- HylaFAX's own sender would not originate V.34: faxsend probed the modem
  from scratch and never loaded `config.ttyds5`, so the call fell back to
  V.17. A manual `AT+FCLASS=1.0`, `AT+F34=14,1,1`, `ATX4DT7910` does
  originate V.34 (`+F34:14,1`), and so does the Diva's Class 2
  (`AT+FCLASS=2`, `AT+FDIS=1,<br>,0,2,0,2,0,0`, `ATX4DT`, `AT+FDT`, page,
  `AT+FET=2`); Class 2 takes its rate from `+FDIS` br, not from `+F34`.
- `mlog` reads commands from stdin and spins on EOF, writing gigabytes to the
  host's tmpfs `/tmp` within minutes. Feed it a blocking stdin
  (`sleep N | divactrl mlog ...`), stop it with `pkill -x divactrl` (mlog is
  a shell wrapper), and trace one B-channel (`-A1`) -- with `-A3` the trace
  ran out within two seconds.

`tools/v34_primary_waveform_decode.py`, which had already decoded our
transmissions perfectly, decodes the card's native 4800/3429 burst perfectly
too (61 image frames plus three RCP, zero invalid). So the bit-level
conventions -- GPC, mapping, trellis, B1, HDLC -- already agreed. The
difference had to be something such a decoder cannot see.

## What differed: orientation relative to PP

V.34 10.1.3.6 defines PP on fixed axes, so an equalizer fitted to PP alone
puts the neighbouring symbols of the same burst on the axes the Recommendation
draws its constellations on. `tools/v34_hdx_training_phase.py` does that and
reports S/S-bar and the symbols after PP:

| Burst | Card (native) | Ours before | Ours after |
|---|---|---|---|
| Phase 3 S/S-bar | 128 x 45/135, 16 x 225/315 | 127 x 0/90, 16 x 180/270, 1 x 0 | as card |
| Phase 3 TRN (16-point) | reference | card's symbols x (-1) | identical to card, 0 degrees |
| Primary S/S-bar (12.5.1) | 128 x 45/135, 16 x 225/315 | 128 x 0/90, 16 x 180/270 | as card |
| Primary B1 | reference | identical | identical |

The card is the one that follows the text. Figure 5 numbers its quarter
superconstellation 0 = (1,1), 1 = (-3,1), 2 = (1,-3), 3 = (-3,-3), so:

- **10.1.3.7 S** alternates point 0 (45 degrees) and point 0 rotated 90
  degrees counterclockwise (135), starting with point 0; **S-bar** alternates
  225 and 315 starting with 225. Our generator alternated by swapping re and
  im from (A, 0) -- 0/90, 45 degrees off the constellation's own axes -- and
  outside 12.5.1 it also started S on its second point, so S-bar began one
  symbol early and the first S point appeared again just before PP.
- **10.1.3.8 TRN** rotates the selected point *clockwise* by In x 90 degrees.
  For the all-ones start of TRN that is point 3 rotated 270 degrees
  clockwise, 3 - 3j, which is the card's first symbol; ours sent -3 + 3j. Our
  `training_constellation_4` is ordered 225/135/45/315, i.e. point 0 rotated
  by In x 90 plus 180 degrees, and the 16-point table is likewise the spec
  rotated by 180 degrees.

Neither shows up in loopback or in an offline decoder trained on PP: our own
receiver and that decoder are rotation-invariant (differential decoding and
the 90-degree-invariant trellis), and the PP fit absorbs the rest. A receiver
that takes its carrier phase from S, or times PP from the S-to-S-bar reversal,
or trains its Phase 3 equalizer data-aided on TRN against PP's phase, is not.
The card's 136-FCS-error control (r20) and clean page (r19) differ in this
alone.

## The change

`spandsp-master/src/v34tx.c`, half-duplex only (`!s->tx.duplex`):

- `get_hdx_s_not_s_baud()` emits exactly 128 S symbols (point 0, then point 0
  rotated 90 degrees counterclockwise) and 16 S-bar symbols (180, then 270
  degrees) for both the 12.3.1.1 Phase 3 and the 12.5.1 primary
  resynchronization, after the existing 70 ms silence, and hands over to PP.
- `get_trn_baud()` sends the 10.1.3.8 point for half-duplex Phase 3 TRN, in
  both constellation sizes.

`V34_HDX_SPEC_TRAINING=0` restores the old points, for A/B against a peer
only. The duplex generators are unchanged: duplex V.34 to this card and to
the other rigs already works, the duplex receivers on both ends are blind to
these rotations, and changing them would need live re-verification on every
peer. They have the same deviations from 10.1.3.7/10.1.3.8 and are the
obvious follow-up.

Regression: `v34-hdx-primary-test`, `-turnaround-test`, `-infoh-test`,
`-channel-test`, `-retrain-test`, `-recovery-test`, `-parameters-test`,
`-startup-recovery-test`, `-high-rate-test` and `fax-v34-test` pass.
`v34_hdx_test` gained `V34_HDX_TX_TAP=<prefix>` (the G.711 codewords each
direction carries), which is how the fixed waveform was checked against the
card's before any live call.
