# How DIAL calls V.8

## The bootpage mechanism (addspv90guide §2.2, §5.4.1)

The ADDSP V.90 software is segmented into **bootpages**. Each page has a
number (guide Table 1):

| # | Page | # | Page |
|---:|---|---:|---|
| 9 | STARTUP | 8 | V.34 |
| 0 | **DIAL** (idle page) | 11 | AT-set offline |
| 1 | V.22 | 12 | AT-set online |
| 2 | V.32 | 13 | V.90A11 |
| 3 | FSK | 14 | V.90D |
| 4 | FAX | 15 | fax protocol |
| 6 | **V.8** | 16 | LL page |
| 7 | INFO | | |

To switch pages the DSP writes the target page number to **bootpage_nr**
(DM `0x3FB0`, read-db offset 0xD0), sets the **bootrequestbit** (bit 8) and
**Boot** bit (bit 6) in **RSTATUS_dbs** (DM `0x3FA5`, offset 0xC5), and idles.
The host then loads the new overlay via IDMA and sets BOOTFINISHED (bit 0xC)
in WSTATUS (DM `0x3EEE`).

The boot sequence is: STARTUP(9) → DIAL(0) → V.8(6) → INFO(7) → V.34(8)/V.90.
"booting from Dial page can be done without any time restrictions."

## DIAL does NOT write bootpage_nr = 6 itself

Disassembling every write to bootpage_nr (`DM($3FB0)`) in the
`0262 DIAL/FSK/FAX.F34` overlay, the only page numbers DIAL writes are:

```
0x0000  (page 0, stay on DIAL / return to idle)
0x000B  (page 11, AT-set offline)
0x000F  (page 15, fax protocol)
0x0010  (page 16, LL page)
0x0011  (page 17, reserved)
0x0028  (40, internal state — not a page number, a sub-state)
0x0004  (page 4, FAX)
```

**V.8 (page 6) is never written to bootpage_nr by this DIAL overlay**, and
DIAL never writes the RSTATUS boot bits at `0x3FA5`.

## The actual V.8 trigger: host supervisor + line-follow-up

Per guide §5.4.2 ("data-pump supervisory rules") and §5.4.1: the V.8 page
load is a **host-side decision**, not a DIAL-side one:

1. The host runs a **training script** while DIAL is active (guide Table 14/15):
   - GEN_SETUP1 = `0x048C` (calling) or `0x068C` (answer mode)
   - GEN_SETUP2 = `0x0030`, WSTATUS = `0x2000` (activate, bit D)
   - Norm_H = `0x0001` (V.8), Norm_L = `0x0100` (V.34+V8), speed selects.
2. DIAL's NORM-mode handler (PM `0x13CC`) reads GEN_SETUP1, sees bit 7
   (NORM OPERATION MODE = "start operation sequence for the norm in
   Norm_L/Norm_H"), clears the bit, and runs the startup DSP init:
   ```
   13cd: AR = DM($3EE1)        ; GEN_SETUP1
   13ce/13cf: conditional ALU  ; test+clear NORM bit
   13d0: DM($3EE1) = AR        ; write back (bit consumed)
   13d2: AR = $0006            ; count for memory-clear helper (NOT page 6)
   13d3: CALL $1279            ; clear 6 words at 0x3FA7
   ...                         ; set up coefficient tables, DSP state
   13f4: CALL $0AC2            ; -> writes bootpage_nr (0 or 0x11)
   ```
3. DIAL updates **TrnProgress** (`DM($3FAD)`, offset 0xCD) and the
   RSTATUS-adjacent status registers (`0x3FAE/0x3FAF/0x3FC0/0x3FC1/0x3FC2`)
   to reflect training progress.
4. The **host supervisor / line-follow-up module** (running on the MIPS, NOT
   on the DSP) polls TrnProgress/RSTATUS. Guide §5.4.2.1:
   *"the request to load the V8 page is generated by the data-pump"* — meaning
   the data-pump's TrnProgress transitions signal the host. The host's
   supervisor state machine (INIT → TRAIN → SUPDATA → RETRAIN → DISC) then
   **loads the V.8 overlay (page 6) via IDMA** and sets BOOTFINISHED.

So the V.8 "call" is a two-stage handshake:
- **DSP side (DIAL):** consume the GEN_SETUP1 NORM bit, run the training
  init, update TrnProgress.
- **Host side (MIPS supervisor):** watch TrnProgress, decide the modem is
  ready, write bootpage_nr=6 + set the RSTATUS boot bits, load the V.8
  overlay (`0x025f V8.F34 Overlay` / `V8.ANA`), set BOOTFINISHED.

## Why this matters for the emulator

DIAL can run standalone and process audio (see `docs/dial_standalone_drive.md`),
and it correctly consumes the GEN_SETUP1 NORM-mode bit (the V.8 *trigger*).
But the **page transition itself** — writing bootpage_nr=6 and loading the
V.8 overlay — is the host supervisor's job, which lives in the MIPS firmware
(`te_dmlt.pm`), the very layer we set out to skip.

To complete the V.8 call without MIPS, the emulator must **model the host
supervisor**: poll `TrnProgress` (0x3FAD) and `RSTATUS` (0x3FA5), and when
DIAL signals training-start, perform the page-6 load (overlay `0x025f`) and
set BOOTFINISHED (0x3EEE bit 0xC). That is a small, well-defined state
machine (guide §5.4.2.1 gives the flow), far simpler than the full TIKRNL
assignment path.

## Confirmed registers

| DM | Offset | Name | Role |
|---|---|---|---|
| `0x3EE0` | 0x00 | GEN_SETUP0 | config |
| `0x3EE1` | 0x01 | GEN_SETUP1 | bit 7 NORM mode (V.8 trigger), bit 3 CH (originate) |
| `0x3EE2` | 0x02 | GEN_SETUP2 | |
| `0x3EEF` | 0x0F | Norm_H | `0x0001` = V.8 |
| `0x3EF0` | 0x10 | Norm_L | `0x0100` = V.34+V8 |
| `0x3EEE` | 0x0E | WSTATUS | bit 0xC = BOOTFINISHED, bit 0xD = activate |
| `0x3FAD` | 0xCD | TrnProgress_dbs | training progress (D0=data, E0=cleardown) |
| `0x3FA5` | 0xC5 | RSTATUS_dbs | bit 8 bootrequest, bit 6 Boot |
| `0x3FB0` | 0xD0 | bootpage_nr | target bootpage number |

DIAL reads GEN_SETUP1 at PM 0x09C8, 0x13CD, 0x145C, 0x1663; the NORM-mode
handler at 0x13CC is the V.8 trigger entry. Harness: `tools/dial_v8_call.py`.
