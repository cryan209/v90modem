# Eicon V90A support check, 9 October 2026

The installed card firmware on eicon420 explicitly advertises V90A:

```
AT+MS=?
(12|V90|V90D|V90A, 11|V34, 10|V32B, 9|V32, ...)
OK
AT+MS=V90A,0
OK
AT+MS?
v90a,0,0,0,0,0
OK
```

These queries used spare `/dev/ttyds5`; the existing four-channel
`bri-test-answerer` service remained running.

Outgoing attempts to 6001 from spare ttyds5/ttyds6, bound to controller 1,
failed before modem negotiation. The first returned NO DIALTONE; subsequent
X3 attempts returned immediate NO CARRIER. Explicit originating number
7910 and disabling DTR/flow-control handling did not change that result.
Controller 1 reported Layer1 Activated and Layer2 UP.

A temporary PCMU V90D SIP answerer registered as 6001 successfully, but its
log recorded no incoming call. A later attempted restart encountered an
occupied SIP port and was not a valid additional answerer run.
The temporary process was stopped afterwards. Each spare Eicon port was
hung up and reset with AT&F; no service or gateway configuration was changed.

Conclusion: **installed firmware exposes and accepts V90A**, but this session
does not establish V90A training or data interoperability. Outgoing ISDN call
setup must be diagnosed before a modem-level result can be obtained.

## Follow-up: originating profile and disconnect cause

The first trials used profile 14, which `divas4linux-master/AT.txt` documents
as incoming autodetection. A corrected trial used `AT&F5` (asynchronous modem),
`AT+iQ=o1`, `AT+iO7910`, `AT+MS=V90A,0`, and disabled DTR/flow control.
The readback showed `+iP5 +iS1/2`. `ATD6001` still returned immediate
NO CARRIER. **Before hangup/reset**, `ATS253?` returned `R253=1c`: Q.931
cause 28, invalid number format/incomplete number. The corrected temporary
answerer registered successfully on SIP port 5079, with no incoming call.
The Eicon port was then hung up and restored to profile 14. The answerer
was bounded by a 100-second timeout.

This points investigation at called-number handling and ISDN-to-SIP routing,
not V.90 DSP. Cisco SSH was reachable, but available authentication failed;
no Cisco configuration was read or changed. A Q.931 trace is required to
identify the rejecting side and the actual called-number information element.

## Cisco trace and successful call setup

Telnet access to the Cisco exposed the actual SETUP called party as `x6001`.
Cisco selected incoming peer 7910, then returned cause 28. The Eicon driver
source `tty_module/atp.c` explicitly prepends `x` when `At.f.Progress == 3`
(X3). Thus the diagnostic retries introduced a nonnumeric destination.
No router routing change was required: using profile 5 and **X4** routed
the call to the temporary 6001 answerer successfully over PCMU.

The call negotiated V.90 in V.8 and reached Phase 4. At +19460 ms our modem
accepted a CRC-valid, 428-bit CPt (drn=17, two constellations), then emitted
3996 mapped TRN2d symbols (D=25, K=20). The Eicon continued repeating CPt;
V.90 did not reach data. Our log subsequently reported V.90 declined and
entered V.34 DATA at 31200 bit/s around +36 seconds. This is a modem startup
interop issue beyond call setup; no payload transfer was graded.

Evidence on Tower: `/tmp/eicon-v90a-x4/server.log` and G.711 taps in the same
directory inside `v90modem-sip`. The Cisco Q.931/CCAPI debugs enabled for
the reproduction were disabled afterwards; existing Q.921 debugging was
left as found. No persistent Cisco configuration was changed.

## Native V90A positive control and Phase 4 isolation

The spare `/dev/ttyds5`, profile 5, controller 1, outgoing identity 7911,
`AT+MS=V90A,0`, and X4 called the native answer service at 7910 over the
same BRI route. It returned **CONNECT V90/LAPM/V42BIS/31200:TX/56000:RX**
and delivered the lab menu. This establishes actual V90A support and a
working native digital peer; it does not establish interoperability with
our software. The answer service was left running.

Preserved native capture: `artifacts/eicon-v90a-self-20261009/native.txt`.
Audio channel 1 is the analogue caller, channel 2 the digital answerer.
The independent analogue Phase 4 decoder reads the native digital stream
with zero demapping errors: 24 barred-Ri symbols, 6000 actual TRN2d symbols,
25017 consecutive ones including MP sync, and CRC-valid Type-1 MP.
Its MP has maximum upstream drn 13, mask 0x0fff, 16-state trellis, and
precoder coefficients (908,1187), (-1026,-378), (922,82).

For our failing call, the card's Audio-1 received PCM matches our TX tap
with an offset of 388 samples. All 127512 samples from 17.0 to 32.939 s
are waveform-identical, including Ri, barred Ri, TRN2d and MP; the byte
differences outside training are only the two G.711 zero polarities.
Thus downstream bearer corruption does not explain this reproduced stall.
Evidence: `artifacts/eicon-v90a-audio-20261009/`, graded by
`tools/eicon_compare_received_audio.py` with `--offset 388 --start 17`.
The Eicon stays at native TRAINPROGRESS 00c0, repeats CPt, and reports
`Supervisor restart retrain: timeout 1 c0 0` after eight seconds.
The meaning of 00c0 is not independently established.

Our complete pre-retrain stream also passes the independent Phase 4
demapper: 1825 CRC-valid Type-0 MPs, zero demapping errors. Native and
software Ri/barred-Ri bytes are identical at the transition; their initial
TRN2d constellation indices and signs agree, with different requested
constellation amplitudes. Self-consistency is insufficient evidence that
the Eicon has acquired our stream.

Controlled hardware experiments, all still repeating CPt and retraining:

| Change | Capture on Tower inside v90modem-sip |
| --- | --- |
| Barred Ri 48T instead of 24T (isolated build only) | /tmp/eicon-v90a-ri48 |
| A-law, controller 2 and SIP extension 2905 | /tmp/eicon-v90a-alaw |
| INFO0d maximum power code 25 (-13 dBm0) | /tmp/eicon-v90a-power13 |
| TRN2d 6048T instead of 3996T | /tmp/eicon-v90a-trn6048 |
| Type-1 MP with zero precoder (isolated build only) | /tmp/eicon-v90a-mp1 |
| Type-1 MP with captured native coefficients (diagnostic only) | /tmp/eicon-v90a-mp1coeff |

The last stream independently grades 868 CRC-valid Type-1 MPs with zero
demapping errors. Captured native coefficients are not valid production
channel estimates; the experiment only tested acceptance of that MP pattern.
The zero-coefficient diagnostic also triggers our analogue trace's Ed
recognition inside its long zero body, so its later demap count is not a
grade of the transmitter. No unsuccessful protocol experiment was applied
to the main implementation. V.90 sections 8.6.3/Table 16, 8.6.4, 8.6.5 and
9.4.1 define the compared MP, Ri and training sequences.

Diagnostic tooling now supports an explicit end sample for a Phase 4 trace,
prints Type-1 precoder fields, and optionally saves canonical decoded CP bits
from the live CP probe. The analogue receiver suite passes. Hardware V.90
data mode and bidirectional payload transfer with our modem remain open.


## DIL receive-gate fixes and native encoder comparison

Two receive gates incorrectly rejected the foreign DIL terminator. V.90
9.3.2.9 permits silence during DIL; 9.3.2.10 then sends 128T S and 16T
S-bar, only 45 ms at 3200 baud. The default requirement for activity in
half of a 300 ms window rejected the real burst (active fractions 0.10
and 0.13). That optional diagnostic gate now defaults to disabled; energy,
echo and retrain-tone checks remain.

A second gate ran a 200 ms structural classifier over mostly preceding
silence even after the V.34 detector confirmed alternating-point S. The
engine now accepts that confirmed alternation without this redundant
classifier; rotation-only candidates retain it. No detector thresholds or
DSP constants changed. Comments cite V.90 9.3.2.9-.10 and V.34 10.1.3.7.

The manual capture regression reproduces the old activity rejection and
checks DIL termination and subsequent accepted CPt on two foreign captures:

```
python3 tools/eicon_dil_termination_test.py artifacts/eicon-v90a-dil2-20261009/live-rx.g711 --alternation-capture artifacts/eicon-v90a-zero-20261009/live-rx.g711
```

Use `ME_V90_DIL_AUTOTERMINATE_CYCLES=0` for these Eicon tests: the generic
one-cycle fallback otherwise ends DIL before the peer requests termination.
That default was not changed for other hardware profiles.

The rebuilt live modem accepts the real second S at +19062 ms, finishes
DIL at segment 16 and accepts CPt at +19247 ms. It still retrains at
+27240 ms; **V90A data mode with our software remains unresolved**.
Capture: `artifacts/eicon-v90a-gates-20261009/`. Temporary answerers exit
on timeout; the native answer service and router configuration are retained.

The native trace's reported 6048-symbol training count included symbols
subsequently decoded as MP. The actual TRN2d is 6000T: 25017 consecutive
ones are 6000 * 25/6 training bits plus MP's 17 sync ones. With the native
CPt, our encoder reproduces all 6000 native PCM bytes exactly, including
the spectral shaper. The new reference comparison checks this directly:

```
./v90_analogue_rx_test --trn2d-reference artifacts/eicon-v90a-self-20261009/card2-tx.g711 artifacts/eicon-v90a-self-20261009/cp.bits 8738 6000
```

The one-sample shifted reference correctly fails. A fresh full native
capture connects at 54666 RX / 31200 TX and shows 30000T TRN1d and DIL
ending after 379 66T segments. Matching TRN1d duration, extending TRN2d
to 6000T, changing Jd lookahead, canonicalizing zero polarity, and advancing
CPt acceptance in isolated diagnostic builds did not establish software
interoperation. These experiments are not production changes.

Extending the card-input comparison back to 12 seconds covers 167512
samples through 32.939 seconds with zero waveform errors (only G.711 zero
polarity differences). This covers the complete relevant downstream Phase 3
and Phase 4 stream, not merely the later training burst.

Validation: analogue receiver suite, capture regression, VPCM all-tests,
data stack, V.42 link, V.34 Phase 2 decode and V.92 procedure evaluator pass.
The full `make test` stops at three K56flex client assertions in its A-law
32k impaired-channel row. The same standalone binary reproduces them and
does not link the changed engine or SpanDSP files; this failure is outside
the validated V.90 change. Hardware connection and payload checks still fail.
